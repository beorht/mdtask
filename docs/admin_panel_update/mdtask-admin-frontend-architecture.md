# Архитектура фронтенда админ-панели mdtask

> Документ описывает архитектуру админ-панели `/admin` по документации
> проекта, актуальной на 02.11.2026.\
> В документе отдельно обозначены **текущая реализация** и
> **предлагаемая целевая организация интерфейса**. Целевая схема ---
> план улучшения, а не утверждение, что эти модули уже существуют в
> коде.

## 1. Назначение и границы

Админ-панель --- основной интерфейс преподавателя в mdtask. Она
позволяет:

-   просматривать общую картину учебного процесса;
-   управлять курсами, заданиями и студентами;
-   проверять работы и пересдачи;
-   анализировать прогресс в SQL, HTML, CSS, Emmet, Python, JavaScript и
    информационной безопасности;
-   управлять итоговыми контрольными;
-   открывать и закрывать доступ к темам;
-   искать студентов, задания, курсы и работы.

**Граница фронтенда:** браузерная часть админки --- EJS-шаблоны,
HTML-разметка, CSS и клиентский JavaScript. Express-маршруты и
`admin-data.js` относятся к серверному слою, но включены в схему, чтобы
показать путь данных к интерфейсу.

## 2. Технологический принцип

Текущая реализация использует:

-   Node.js + Express 5;
-   EJS для серверного рендеринга страниц;
-   обычные CSS и JavaScript без React/Vue и без этапа frontend-сборки;
-   SQLite через серверный слой `src/db`;
-   локальные статические ресурсы из `public/`.

**Архитектурное решение:** сохранять server-rendered подход. Для
оптимизации интерфейса не требуется переписывать админку на
SPA-фреймворк. Улучшения можно внедрять постепенно в существующей
структуре.

## 3. Текущая архитектура: общий поток

``` mermaid
flowchart TD
    A["Преподаватель в браузере"] --> B["HTTP-запрос /admin/*"]
    B --> C["Express: src/server.js"]
    C --> D["adminRoutes: src/routes/admin.js"]
    D --> E["requireRole('teacher')"]
    E --> F["Общие res.locals<br/>user, view, icon, STATUS_META,<br/>flash, nav, reviewCount"]
    F --> G["Маршрут страницы<br/>admin.js или admin-*.js"]
    G --> H["admin-data.js / профильный data-модуль"]
    H --> I["src/db и другие серверные сервисы"]
    I --> J[("SQLite / файловый контент / журналы")]
    H --> K["Данные страницы + фильтры"]
    K --> L["render(res, template, nav, locals)"]
    L --> M["EJS: src/views/admin"]
    M --> N["HTML-ответ"]
    N --> O["Браузер"]
    O --> P["admin.css + admin.js"]
    P --> Q["Интерактивность: меню, поиск,<br/>тема, фильтры, подтверждения"]
```

### 3.1. Серверный конвейер страницы

Типичный путь страницы:

``` text
GET /admin/...
    ↓
requireRole('teacher')
    ↓
общие res.locals
    ↓
маршрут admin.js или подключённого admin-*.js
    ↓
получение и подготовка данных
    ↓
render(res, template, nav, locals)
    ↓
EJS-шаблон + партиалы
    ↓
HTML + admin.css + admin.js
```

Маршрут читает параметры запроса (`req.query`), нормализует фильтры,
вызывает функцию подготовки данных и передаёт результат шаблону.
Бизнес-правила статусов, очереди и агрегатов вынесены в
`src/lib/admin-data.js` и профильные модули.

## 4. Структура фронтенда по слоям

``` text
src/
├── routes/
│   ├── admin.js                  # основной роутер и общая инфраструктура
│   ├── admin-exam.js             # итоговая контрольная
│   ├── admin-web-exam.js         # WEB-контрольная
│   ├── admin-emmet.js            # Emmet
│   ├── admin-html.js             # HTML
│   ├── admin-css.js              # CSS
│   ├── admin-python-course.js    # начальный Python
│   ├── admin-js-course.js        # JavaScript
│   └── admin-locks.js            # доступ к темам
│
├── lib/
│   ├── admin-data.js             # агрегаты и правила данных админки
│   ├── admin-locks.js            # данные раздела замков
│   ├── admin-view.js             # форматирование, SVG-иконки, query-строки
│   └── subject-topics.js         # реестр предметов/тем для замков
│
└── views/
    └── admin/
        ├── *.ejs                 # страницы админки
        └── partials/
            ├── start.ejs        # начало документа, topbar, shell, flash
            ├── end.ejs          # завершение shell и confirm dialog
            ├── sidebar.ejs      # боковая навигация
            ├── status.ejs       # бейдж статуса
            ├── empty.ejs        # пустое состояние
            ├── ib-signals.ejs   # сигналы ИБ
            └── ib-oral.ejs      # материалы устной проверки

public/
├── css/
│   └── admin.css                # самостоятельные стили админки
└── js/
    └── admin.js                 # общая клиентская логика админки
```

Важно: админка использует собственные `admin.css` и `admin.js`. Она не
подключает студенческие `theme.css` и `components.css`. Это фактическая
граница оформления между двумя интерфейсами.

## 6. Каркас каждой страницы

Общего layout-движка сейчас нет. Страницы подключают начальный и
конечный партиалы:

``` ejs
<%- include('partials/start') %>

<!-- Содержимое конкретной страницы -->

<%- include('partials/end') %>
```

### 6.1. `partials/start.ejs`

Отвечает за:

-   HTML `<head>`;
-   установку темы до загрузки CSS, чтобы избежать вспышки другой темы;
-   подключение локальных шрифтов, `admin.css` и `admin.js` (`defer`);
-   верхнюю панель;
-   заголовок текущего раздела;
-   глобальный поиск;
-   переключатель темы;
-   индикатор очереди проверки;
-   меню пользователя;
-   открытие основного контейнера `.a-shell`;
-   вывод flash-сообщения.

### 6.2. `partials/sidebar.ejs`

Отвечает за:

-   навигационные группы;
-   ссылки на разделы;
-   активное состояние по ключу `nav`;
-   бейдж количества работ на проверке.

### 6.3. `partials/end.ejs`

Отвечает за:

-   закрытие основного контейнера;
-   общий `<dialog>` для подтверждения опасных действий;
-   завершение HTML-документа.

### 6.4. Повторно используемые партиалы

  Партиал            Назначение
  ------------------ ------------------------------------------
  `status.ejs`       Единое отображение статуса
  `empty.ejs`        Пустое состояние списка
  `ib-signals.ejs`   Блок сигналов целостности/антисписывания
  `ib-oral.ejs`      Информация для устной проверки

## 7. Клиентский JavaScript

Текущий общий файл: `public/js/admin.js`.

Он отвечает за:

1.  мобильное открытие/закрытие сайдбара и backdrop;
2.  выпадающее меню пользователя;
3.  переключение темы;
4.  живой глобальный поиск через `GET /admin/search?format=json`;
5.  закрытие flash-сообщений;
6.  общий диалог подтверждения действий через `data-confirm`;
7.  автоматическую отправку фильтров через `data-autosubmit`.

Принцип: `admin.js` содержит общие взаимодействия оболочки. Логику
конкретных предметных тренажёров и редакторов не следует без
необходимости переносить в этот файл.

## 8. Слой данных, который обслуживает интерфейс

Фронтенд не должен самостоятельно вычислять учебные статусы или строить
сложные агрегаты из сырых данных. Это делает серверный слой.

### 8.1. Основные функции данных

`src/lib/admin-data.js`:

-   `loadContext()` --- загружает пользователей, курсы, задания, сдачи и
    строит индексы;
-   `dashboard()` --- показатели главной страницы и последние работы;
-   `filterWorks()` --- фильтрация списка работ;
-   `tabCounts()` --- счётчики вкладок;
-   `nextInQueue()` --- следующая работа очереди;
-   `assignmentRows()` / `assignmentDetail()` --- список и детали
    заданий;
-   `studentRows()` / `studentProfile()` --- список и профиль студента;
-   `courseRows()` / `courseDetail()` --- список и детали курсов;
-   функции SQL-аналитики и результатов ИБ;
-   `search()` --- глобальный поиск.

### 8.2. Общий контракт между маршрутом и шаблоном

``` text
Маршрут:
  1. получает req.query / req.params;
  2. нормализует и проверяет фильтры;
  3. получает контекст и агрегаты;
  4. вызывает render(template, nav, locals).

Шаблон:
  1. получает подготовленные locals;
  2. отображает состояние страницы;
  3. использует общие партиалы;
  4. отправляет действия обычными формами/ссылками или fetch там,
     где это уже предусмотрено.
```

Не следует помещать бизнес-логику в EJS или дублировать правила статусов
в браузерном JS.

## 9. Текущие UI-правила и состояния

### 9.1. Статусы

Статусы передаются не только цветом: каждый статус имеет текст и
символ/иконку.

  Ключ              Отображение
  ----------------- --------------
  `pending`         На проверке
  `resubmitted`     Пересдача
  `done`            Выполнено
  `not_done`        Не выполнено
  `sent_back`       На пересдаче
  `overdue`         Просрочено
  `not_submitted`   Не сдано
  `in_progress`     В процессе

Шаблон `status.ejs` использует общий словарь `STATUS_META`.

### 9.2. Обязательные состояния страниц

При оптимизации страниц сохранять понятные состояния:

-   обычное состояние с данными;
-   загрузка/обновление, если операция выполняется асинхронно;
-   пустой результат;
-   ошибка загрузки или действия;
-   подтверждение опасного действия;
-   успешное действие через flash;
-   заблокированное/недоступное состояние, если применимо.

Для списков использовать единый `empty.ejs`, где это подходит.

## 10. Целевая организация фронтенда для дальнейшей оптимизации

Следующая схема --- **рекомендация по рефакторингу**, а не описание уже
существующих файлов. Она сохраняет EJS и текущие URL, но делает UI более
последовательным и удобным для поддержки.

``` mermaid
flowchart TD
    APP["Admin UI"]
    APP --> SHELL["Admin Shell"]
    APP --> PAGES["Страницы"]
    APP --> UI["Общие UI-компоненты"]
    APP --> CLIENT["Клиентские модули"]

    SHELL --> TOP["Topbar"]
    SHELL --> SIDE["Sidebar"]
    SHELL --> CONTENT["Main content"]
    SHELL --> FEEDBACK["Flash / Dialog / Empty"]

    PAGES --> OVERVIEW["Обзор"]
    PAGES --> LEARNING["Обучение"]
    PAGES --> CHECK["Проверка"]
    PAGES --> ANALYTICS["Аналитика"]
    PAGES --> SUBJECTS["Предметы и тренажёры"]
    PAGES --> SYSTEM["Система"]

    UI --> BUTTONS["Кнопки"]
    UI --> BADGES["Статусы и бейджи"]
    UI --> FILTERS["Фильтры"]
    UI --> TABLES["Таблицы"]
    UI --> FORMS["Формы"]
    UI --> CARDS["Карточки показателей"]
    UI --> EMPTY["Пустые состояния"]

    CLIENT --> NAVJS["navigation.js"]
    CLIENT --> SEARCHJS["search.js"]
    CLIENT --> THEMEJS["theme.js"]
    CLIENT --> FILTERJS["filters.js"]
    CLIENT --> DIALOGJS["dialog.js"]
    CLIENT --> PAGEJS["page-specific JS"]

    SHELL --> EJS["EJS partials"]
    PAGES --> EJS
    UI --> EJS
    EJS --> CSS["admin.css / разделённые CSS-модули"]
    EJS --> HTML["Server-rendered HTML"]
```

### 10.1. Предлагаемое логическое деление

  -----------------------------------------------------------------------
  Область                             Ответственность
  ----------------------------------- -----------------------------------
  `AdminShell`                        Общий каркас, topbar, sidebar,
                                      основная область

  `Navigation`                        Группы меню, активный пункт,
                                      счётчики

  `Overview`                          Сводные показатели и приоритетные
                                      действия

  `Learning`                          Курсы, задания, студенты

  `Review`                            Очередь, просмотр сдачи, вердикт,
                                      переход к следующей работе

  `Analytics`                         SQL, ИБ и статистика предметов

  `Subjects`                          Emmet, HTML, CSS, Python,
                                      JavaScript

  `Exams`                             IB- и WEB-контрольные

  `Access`                            Замки тем и настройки

  `UI primitives`                     Кнопки, формы, таблицы, бейджи,
                                      диалоги, пустые состояния
  -----------------------------------------------------------------------

Это логические зоны интерфейса. Необязательно создавать отдельный
JavaScript-файл или EJS-файл для каждого компонента, если компонент
прост.

### 10.2. Возможное разбиение клиентского JS

Текущее поведение `admin.js` можно оставить как есть на первом этапе.
Если файл станет сложно поддерживать, выделять модули постепенно:

``` text
public/js/admin/
├── core.js          # инициализация и общие утилиты
├── navigation.js    # sidebar и мобильное меню
├── search.js        # живой глобальный поиск
├── theme.js         # переключатель темы
├── filters.js       # data-autosubmit и фильтры
├── dialogs.js       # data-confirm и dialog
└── feedback.js      # flash-сообщения
```

Это целевая структура. При её внедрении нужно сохранить совместимость с
текущими атрибутами `data-*` и не подключать один модуль дважды.

### 10.3. Возможное разбиение CSS

Сейчас админка оформлена самостоятельным `public/css/admin.css`. Не
нужно сразу дробить его. Сначала стоит определить устойчивые группы
стилей и только затем выделить:

``` text
public/css/admin/
├── tokens.css       # цвета, типографика, размеры, отступы
├── shell.css        # topbar, sidebar, layout
├── components.css   # кнопки, формы, таблицы, карточки, бейджи
├── utilities.css    # вспомогательные классы
└── responsive.css   # адаптивные состояния
```

Можно оставить единый `admin.css` как точку подключения этих файлов,
если проект по-прежнему работает без сборки.

## 11. Рекомендуемая визуальная иерархия

Предлагаемая структура типовой страницы:

``` text
┌──────────────────────────────────────────────────────────────┐
│ Логотип / Название раздела     Поиск    Тема   Проверка  Профиль│
├───────────────┬──────────────────────────────────────────────┤
│               │ Заголовок страницы                           │
│ Навигация     │ Краткое пояснение / основное действие         │
│               │                                              │
│ Обзор         │ Фильтры и поиск по текущему разделу            │
│ Обучение      │                                              │
│ Проверка      │ Основной контент: таблица / карточки / форма  │
│ Предметы      │                                              │
│ Аналитика     │ Пагинация / итог / вторичные действия          │
│ Система       │                                              │
│               │                                              │
└───────────────┴──────────────────────────────────────────────┘
```

Правила для нового UI:

-   одна основная цель на экран;
-   главное действие страницы визуально выделено;
-   фильтры находятся рядом со списком, к которому относятся;
-   вторичные и опасные действия не конкурируют с основным;
-   длинные таблицы не перегружаются второстепенными столбцами;
-   статус всегда имеет текстовую подпись, а не только цвет;
-   мобильная навигация использует уже предусмотренные
    sidebar/backdrop-механизмы.

## 13. Ограничения и важные зависимости

1.  Админка защищена `requireRole('teacher')`; интерфейсная навигация не
    заменяет серверную проверку доступа.
2.  Фильтры должны валидироваться на сервере, даже если элементы UI
    ограничивают варианты.
3.  Статусы и правила дедлайнов должны оставаться в серверной логике
    `admin-data.js` и связанных сервисах.
4.  Предметные страницы имеют собственные модули маршрутов и разные
    наборы данных; общий UI не должен стирать предметную специфику.
5.  Замки тем сейчас подключены не ко всем предметам: в документации
    отмечены HTML и CSS как подключённые, остальные интеграции ожидают
    выполнения.
6.  Админка изолирована от студенческой темы и CSS. При унификации нужно
    учитывать это разделение.
7.  Локальные ресурсы важны для работы в аудиториях без интернета: не
    вводить внешние CDN и удалённые шрифты.
8.  Реальные данные студентов и файловые каталоги не должны
    затрагиваться при UI-рефакторинге.

## 14. План реализации по этапам

### Этап 1. Инвентаризация и базовые компоненты

-   проверить все EJS-страницы админки;
-   зафиксировать повторяющиеся элементы;
-   определить единые токены цветов, размеров, отступов и типографики;
-   проверить доступность кнопок, полей, фокуса и клавиатурной
    навигации;
-   не менять бизнес-логику и URL.

### Этап 2. Каркас и навигация

-   улучшить `start.ejs`, `sidebar.ejs`, `end.ejs`;
-   сгруппировать пункты меню;
-   сохранить активный пункт и `reviewCount`;
-   проверить мобильное меню и backdrop;
-   обеспечить единое поведение topbar на всех страницах.

### Этап 3. Обзор и проверка работ

-   сначала оптимизировать dashboard;
-   затем очередь и страницу проверки;
-   сохранить переход `next=1` к следующей работе;
-   сделать предпросмотр и вердикты визуально приоритетными.

### Этап 4. Обучение

-   унифицировать списки студентов, курсов и заданий;
-   согласовать фильтры, сортировку, пустые состояния;
-   привести карточки деталей к общей структуре.

### Этап 5. Аналитика и предметные страницы

-   привести матрицы «студент × упражнение/шаг» к общему паттерну;
-   унифицировать карточки студента и действия сброса;
-   сохранить специфичные данные и сигналы каждого предмета.

### Этап 6. Контрольные, доступ и полировка

-   оптимизировать IB/WEB контрольные;
-   сделать безопаснее и понятнее формы замков тем;
-   проверить ошибки, подтверждения, flash и адаптивность;
-   провести регрессионную проверку маршрутов и форм.

## 15. Критерии готовности

-   все существующие разделы и действия доступны;
-   URL и серверные контракты не сломаны без отдельного согласования;
-   одинаковые элементы выглядят и ведут себя одинаково;
-   навигация понятна без знания внутренних названий файлов;
-   основные задачи преподавателя выполняются с минимальным количеством
    переходов;
-   фильтры сохраняют корректные значения и не обходят серверную
    валидацию;
-   пустые состояния, ошибки и подтверждения оформлены единообразно;
-   интерфейс работает на десктопе, планшете и телефоне;
-   страницы работают без внешних CDN;
-   тесты маршрутов, проверки и существующих действий проходят.

## 16. Что не следует делать на первом этапе

-   переписывать админку на React/Vue только ради обновления дизайна;
-   менять SQLite или серверную архитектуру ради фронтенд-оптимизации;
-   переносить вычисление статусов и прав доступа в браузер;
-   объединять все предметные тренажёры в один сложный клиентский
    модуль;
-   удалять существующие функции ради упрощения меню;
-   одновременно менять дизайн, маршруты, схему БД и бизнес-логику.

## 17. Итоговая архитектурная позиция

**Рекомендуемый путь:** оставить Express + EJS + Vanilla JS, сохранить
серверный рендеринг и текущие бизнес-модули, но системно улучшить
оболочку, навигацию, повторно используемые UI-паттерны и организацию
клиентских сценариев.

Первый практический объект рефакторинга --- общий каркас (`start.ejs`,
`sidebar.ejs`, `end.ejs`, `admin.css`, `admin.js`). После него ---
dashboard и очередь проверки, потому что они задают ежедневный рабочий
сценарий преподавателя. Затем можно последовательно приводить остальные
разделы к общей системе компонентов.

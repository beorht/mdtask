# Этап 0 — UI-прототип платформы практических заданий

## Контекст

Проект — веб-платформа для сдачи практических заданий в стиле mdBook (см.
`docs/plan.md` за полным описанием сущностей и флоу). Это первый sub-project:
чисто визуальный прототип на фейковых данных, без БД и без реальной
бизнес-логики. Цель — обкатать дизайн (сайдбар/центр/TOC, light/dark темы,
карточки заданий, блок загрузки, панель проверки препода) до того как
подключать SQLite и реальную авторизацию.

Итоговый стек проекта (используется начиная с этого этапа, чтобы вёрстка и
роутинг переносились без переписывания):

- **Backend:** Node.js + Express
- **Шаблонизатор/рендер:** EJS + `markdown-it` (тот же парсер MD и на
  сервере, и — впоследствии — в превью редактора)
- **БД (будущие этапы):** SQLite через `better-sqlite3`, сырой SQL, без ORM
- **Авторизация (будущие этапы):** вход по Student ID без пароля;
  аккаунты создаёт администратор заранее в БД

На этом этапе БД и авторизация **не реализуются** — только мокап логина и
фейковые JSON-файлы вместо запросов к БД.

## Цель и границы

**Входит:**
- Express-приложение, отдающее EJS-страницы на фейковых данных из `fixtures/*.json`.
- Пример контента заданий как mini mdBook-репозиторий (`content/SUMMARY.md` + `content/src/**/*.md`), рендерящийся через `markdown-it`.
- Все ключевые экраны (см. ниже), обе темы (light/dark), адаптивный сайдбар.
- CSS-система в стиле mdBook (типографика, цвета, статус-бейджи).

**Не входит:**
- БД, реальная авторизация, сохранение состояния между запросами.
- Реальная загрузка/хранение файлов сдач (только визуальная drag&drop зона со списком фейковых "уже загруженных" файлов).
- Real-time валидация, уведомления, API вне текущего Express-сервера.
- Автотесты (проверка вручную в браузере).

## Данные (fixtures)

Фейковые JSON-файлы отражают модель из `docs/plan.md` (раздел 3, 8, 9), но
без реального хранения:

- `users.json` — несколько студентов и один преподаватель, с `role`.
- `courses.json` / `assignments.json` — `assignments` ссылаются на путь к
  `.md`-файлу в `content/src/` (не хранят текст), плюс `target_type:
  'group'|'individual'`, `target_student_id`, `due_date`.
- `submissions.json` — статусы `pending/done/not_done`, `comment`,
  `parent_submission_id` для демонстрации вкладок "Основная сдача" /
  "Пересдача" на странице задания.

Сервер на старте один раз читает `content/SUMMARY.md` через
`summary-parser.js`, строит дерево для сайдбара и сшивает его с
`assignments.json` по пути файла — так сайдбар и страница задания берут
текст из одного и того же MD-файла, как в итоговой архитектуре (план,
раздел 10).

## Экраны

1. **Login** (`/login`) — поле Student ID, без валидации пароля; submit
   ищет пользователя в `users.json` по ID и кладёт его в сессию
   (`express-session`, in-memory, без БД) — только чтобы отличать
   студента/препода при навигации по прототипу.
2. **Student dashboard** (`/`) — список курсов → заданий с бейджами статуса
   (🟡 на проверке / 🟢 выполнено / 🔴 не выполнено / ⚪ не сдано), датой
   дедлайна, иконкой вложения. Индивидуальные задания — в отдельной
   подсекции "Мои доп. задания".
3. **Assignment view (student)** (`/assignment/:id`) — хлебные крошки,
   рендер MD, справа TOC по заголовкам + бейдж статуса, снизу блок
   drag&drop (визуальный, без реальной отправки) со списком "уже
   загруженных" файлов и кнопками заменить/удалить. Если есть
   `parent_submission_id` — вкладки "Основная сдача"/"Пересдача".
4. **Teacher dashboard** (`/teacher`) — список курсов преподавателя.
5. **Assignment editor (teacher)** (`/teacher/assignment/:id/edit`) —
   слева textarea с MD, справа live-превью (тот же layout, что увидит
   студент). Превью обновляется через `editor-preview.js` (debounce +
   fetch на `/api/preview` рендерящий через `markdown.js`, либо
   клиентский markdown-it — решается при реализации).
6. **Submissions table (teacher)** (`/teacher/assignment/:id/submissions`)
   — таблица студентов группы, статус-переключатель в один клик,
   разворачивающееся поле комментария. Разворот сдачи показывает файлы
   (фейковые ссылки) и кнопку "Разрешить пересдачу".

## Дизайн-система

Переменные тем в `theme.css` (значения — из `docs/plan.md`, раздел 7):

- Light: фон `#fafafa`, сайдбар `#f7f7f7`, текст `#1f1f1f`, акцент `#4183c4`.
- Dark: фон `#1d1f21`, текст `#c8c9db`, акцент чуть ярче для контраста.
- Статус-бейджи: зелёный/красный/жёлтый-серый — общие классы `.badge-done`,
  `.badge-not-done`, `.badge-pending`.
- Шрифты: serif для текста задания, monospace для блоков кода (через
  Google Fonts или системный fallback — уточняется при реализации, не
  блокирует дизайн).
- Layout: сайдбар fixed ~280px, центр max-width ~750–800px по центру,
  правая TOC-панель опционально скрывается на узких экранах; на мобильном
  сайдбар — гамбургер-меню.

## Ошибки и краевые случаи (прототип)

- Несуществующий `:id` в роуте → простая 404-страница в стиле сайта (не
  голый Express error).
- Пустой список сдач/заданий → placeholder-текст вместо пустой таблицы.
- Логика прав (студент не должен видеть чужие индивидуальные задания или
  таблицу сдач препода) — реализуется на уровне роутов даже в прототипе
  (проверка роли из сессии), чтобы не переучивать паттерн на Этапе 1.

## Тестирование

Ручная проверка через dev-сервер (`run` skill) по каждому экрану:
- обе темы (light/dark) переключаются и не ломают вёрстку;
- сайдбар корректно строится из `SUMMARY.md` и подсвечивает активный пункт;
- адаптив: сайдбар сворачивается в гамбургер на узком экране;
- переходы между ролями (студент/препод) показывают правильный набор
  экранов и не дают доступа к чужим разделам.

Автотесты не пишутся на этом этапе.

# Платформа для практических заданий (Moodle-lite в стиле mdBook)

## 1. Суть проекта

Веб-платформа, где:
- **Студент** видит список заданий, открывает задание, загружает свою практическую работу, может отредактировать/перезагрузить до проверки.
- **Преподаватель** загружает материалы заданий (текст в Markdown), просматривает сданные работы, выставляет статус **"Выполнено" / "Не выполнено"** (и опционально — комментарий).
- Внешний вид всего сайта — как у **mdBook**: левый сайдбар с деревом разделов/заданий, чистая типографика, минимализм, светлая/тёмная тема.

Это НЕ LMS с оценками по баллам, тестами и т.п. — упрощённый трекер практик с бинарным статусом сдачи.

---

## 2. Роли и права

| Роль | Возможности |
|---|---|
| **Студент** | Вход по логину/паролю (или через уже существующую систему ID, см. ниже), просмотр списка своих курсов/заданий, открытие задания (рендер MD), загрузка файла(ов) решения, редактирование/замена файла до дедлайна или до проверки, просмотр статуса и комментария преподавателя |
| **Преподаватель** | Создание курса → раздела → задания, загрузка/редактирование MD-контента задания, прикрепление файлов-примеров, просмотр списка сдач по группе, открытие сдачи студента, выставление статуса (done/not done), написание комментария, история изменений статуса |
| **Администратор** (опционально, роль может совпадать с твоей) | Управление пользователями, группами, курсами, ролями; массовый импорт студентов (можно переиспользовать вашу систему student ID) |

---

## 3. Структура сущностей (модель данных)

```
User (id, ФИО, роль, группа, логин/hash пароля)
Group (id, название, куратор)
Course (id, название, преподаватель)
Section (id, course_id, название, порядок)      -- аналог главы в mdBook
Assignment (id, section_id, title, content_md, attachments[], due_date, order)
Submission (id, assignment_id, student_id, files[], status[done/not_done/pending],
            comment, submitted_at, checked_at, checked_by)
```

`Section` и `Assignment` образуют то самое дерево, которое рендерится как сайдбар mdBook (SUMMARY.md).

## 4. Пользовательские сценарии (флоу)

**Студент:**
1. Логин → попадает на Dashboard: список курсов → список заданий (статус: не сдано / на проверке / выполнено / нужно исправить).
2. Открывает задание → читает MD-описание (условие, критерии) → видит форму загрузки.
3. Загружает файл(ы)/архив/ссылку на репозиторий.
4. Пока статус "на проверке" — может заменить файл.
5. После проверки видит статус + комментарий преподавателя. Если "не выполнено" — может перезагрузить снова (флоу возвращается на проверку).

**Преподаватель:**
1. Логин → Dashboard преподавателя: список курсов, где он ведёт.
2. Создаёт/редактирует раздел и задание — пишет MD прямо в браузере (редактор с превью, как в mdBook: слева пишешь, справа рендер).
3. Открывает вкладку "Сдачи" по заданию → таблица студентов группы со статусами.
4. Кликает на сдачу → скачивает/просматривает файл → ставит done/not done + комментарий.

## 5. Технический стек (предложение)

- **Backend:** Node.js (Express/Fastify) или C#/ASP.NET Core (учитывая твой опыт) — REST API.
- **База данных:** PostgreSQL (или SQLite для старта/пилота).
- **Frontend:** статическая генерация в духе mdBook — можно взять React/Next.js SPA с кастомным сайдбар-роутингом, либо серверный рендеринг MD в HTML (markdown-it / remark) + минимальный JS для интерактивности (загрузка файлов, формы).
- **Хранение файлов:** локальная файловая система на первом этапе (папки по course/assignment/student), позже — S3-совместимое хранилище.
- **Авторизация:** JWT или сессии; в будущем можно связать с вашей системой student ID (см. `student-id-scheme`).
- **Рендер Markdown:** единая библиотека и на фронте (превью при редактировании) и при показе задания студенту — важно для консистентности с mdBook-стилем (поддержка блоков кода с подсветкой, таблиц, изображений).

## 6. Этапы разработки (MVP → расширение)

**Этап 0 — Прототип UI (без бэкенда)**
- Верстка дизайн-системы (сайдбар, страница задания, страница сдач) на фейковых данных.

**Этап 1 — MVP**
- Auth (студент/преподаватель), CRUD курсов/разделов/заданий (только препод), рендер MD.
- Загрузка файла студентом, простой список сдач, ручное выставление статуса.

**Этап 2**
- Комментарии к сдаче, история статусов, уведомления (на email/Telegram) о новой сдаче или о проверке.
- Множественная загрузка файлов / drag&drop, ограничение типов/размера.

**Этап 3**
- Группы/потоки, массовый импорт студентов, статистика по группе (% выполненных), экспорт отчёта (например, для тех самых дипломных документов).
- Возможно — интеграция с вашей системой student ID и классрум-контролем (единая экосистема Synergy).

**Этап 4 (опционально)**
- Версионирование сдач (история загрузок, не только последняя), встроенный просмотр кода/файлов без скачивания, git-репозиторий как способ сдачи.

## 7. Дизайн-концепция (в стиле mdBook)

**Общая структура страницы** — три зоны, как в mdBook:
1. **Левый сайдбар** (fixed, ~280px) — дерево: Курс → Раздел → Задание. Сворачиваемые разделы, активный пункт подсвечен полосой слева. Внизу сайдбара — переключатель темы (light/dark) и профиль пользователя.
2. **Центральная колонка** (max-width ~750–800px, по центру) — контент: рендер MD задания, ниже — блок сдачи (для студента) или таблица сдач (для препода).
3. **Правая мини-панель (опционально)** — "On this page" оглавление по заголовкам текущего MD (как в mdBook), плюс блок статуса задания (бейдж: 🟡 На проверке / 🟢 Выполнено / 🔴 Не выполнено).

**Типографика:**
- Основной шрифт — как у mdBook: системный serif/sans (например, "Source Serif Pro" для текста задания, моноширинный "Source Code Pro"/"Fira Code" для блоков кода).
- Крупные читаемые заголовки, умеренный line-height (1.6–1.7) для длинных текстовых условий заданий.

**Цветовая схема:**
- Светлая тема: фон `#ffffff`/`#fafafa`, текст `#1f1f1f`, акцент — синий/бирюзовый (как у mdBook `#4183c4` или можно взять фирменный цвет колледжа), сайдбар чуть светлее фона `#f7f7f7` с тонкой границей.
- Тёмная тема: фон `#1d1f21` / `#282c34` (аналог "Ayu"/"Navy" темы mdBook), текст `#c8c9db`, акцент — тот же бирюзовый, но чуть ярче для контраста.
- Статус-бейджи: зелёный (выполнено), красный (не выполнено), жёлтый/серый (на проверке) — как метки в углу карточки задания и в списке.

**Компоненты, специфичные под задачу платформы (сверх стандартного mdBook):**
- **Карточка задания в списке** — название, короткий бейдж статуса, дата дедлайна, иконка вложения.
- **Блок загрузки** под текстом задания — drag&drop зона + список уже загруженных файлов с кнопками "заменить"/"удалить" (пока не проверено).
- **Панель проверки у преподавателя** — справа/снизу от контента задания: список студентов группы, у каждого — статус-переключатель (done/not done) в один клик + текстовое поле комментария, разворачивающееся по клику.
- **Редактор MD у преподавателя** — двухпанельный (слева textarea/CodeMirror с MD, справа live-превью в том же стиле, в котором это увидит студент) — это гарантирует, что то, что препод пишет, выглядит один в один как у студента.

**Навигация/мелочи:**
- Хлебные крошки над заголовком (Курс / Раздел / Задание) — как в mdBook путь по SUMMARY.
- Поиск по Markdown-контенту заданий (как встроенный поиск mdBook) — полезно для препода при большом количестве материалов.
- Адаптивность: на мобильном сайдбар сворачивается в гамбургер-меню (как в mdBook на узких экранах).

## 8. Принятые решения (уточнено)

- **Сроки/дедлайны:** устанавливает преподаватель при создании задания. По истечении срока задание автоматически закрывается — загрузка/редактирование сдачи блокируется (нужен статус `closed` у Assignment + серверная проверка `now > due_date` перед приёмом файла).
- **Файлы сдачи:** несколько файлов на сдачу, разрешённые форматы — `.zip`, `.rar` (архивы с практической работой). Нужна валидация MIME/расширения и разумный лимит размера.
- **Переработка после "не выполнено":** возможна точечно — по решению преподавателя открывается повторная загрузка **для конкретного студента** (не массово для всей группы). Это отдельное действие препода на сдаче: кнопка "Разрешить пересдачу" → статус submission возвращается в `pending`/переоткрыт для загрузки, даже если общий дедлайн уже прошёл.
- **Авторизация:** используется существующая система student ID (см. `student-id-scheme`) — отдельную систему логинов для студентов заводить не нужно, платформа работает поверх неё.
- **Уведомления:** не нужны на данном этапе — исключены из MVP и из ближайших этапов.
- **Типы заданий (важное уточнение модели данных):**
  - **Общее задание** — назначается на весь Course/Section, видно и сдаётся всеми студентами группы.
  - **Индивидуальное доп. задание** — назначается конкретному студенту (student_id), видно только ему.

  Модель `Assignment` расширяется полем `target`:
  ```
  Assignment (..., target_type: 'group' | 'individual', target_student_id: nullable)
  ```
  В сайдбаре/списке индивидуальные задания можно визуально выделять (например, значок или отдельная подсекция "Мои доп. задания") у конкретного студента, при этом у остальных студентов группы они вообще не отображаются.

## 9. Дополнительные решения

- **Пересдача:** преподаватель открывает её в один клик прямо из списка сдач, без отдельного лога/причины.
- **Лимиты на файлы:** ограничения на размер архива и количество файлов не нужны.
- **История пересдач:** под старым (неудачным) заданием/сдачей открывается вкладка **«Пересдача»** — старая сдача остаётся видна в истории, новая появляется рядом во вкладке, ничего не перезаписывается.
  ```
  Submission (id, assignment_id, student_id, files[], status, comment,
              submitted_at, checked_at, checked_by, parent_submission_id)
  ```
  `parent_submission_id` связывает пересдачу с исходной неудачной попыткой — на UI это и рендерится как вкладки "Основная сдача" / "Пересдача" внутри одной карточки задания.

## 10. Хранение контента заданий (архитектура файлов)

Выбран **вариант А** — индивидуальные задания создаются с нуля, отдельно от общих (без «форка»/копирования текста).

Контент задания хранится не только в БД, а **как настоящий mdBook-проект**:

- Текст каждого задания — отдельный `.md`-файл в директории `src/` (структура один в один как в реальном mdBook-репозитории).
- Дерево заданий/разделов задаётся файлом **`SUMMARY.md`** в корне `src/` — именно он определяет, что показывается в сайдбаре и в каком порядке (как в обычном mdBook).

```
course-<id>/
├── SUMMARY.md              -- дерево: разделы → задания (+ ссылки на .md файлы)
└── src/
    ├── section-1/
    │   ├── task-1.md
    │   └── task-2.md
    ├── section-2/
    │   └── task-1.md
    └── individual/
        └── student-<id>/
            └── extra-task.md   -- индивидуальные доп. задания, отдельная поддиректория
```

Из этого следует:
- **Запись:** когда преподаватель создаёт/редактирует задание через веб-редактор, бэкенд пишет/обновляет соответствующий `.md`-файл в `src/` и добавляет/обновляет строку в `SUMMARY.md`.
- **Чтение/рендер:** страница задания у студента и препода рендерит именно этот `.md`-файл (тем же парсером, что и остальной mdBook-стиль сайта) — гарантирует полную визуальную идентичность с общим дизайном.
- **Индивидуальные задания** физически лежат в отдельной поддиректории (`individual/student-<id>/`) и в `SUMMARY.md` попадают только в персональную ветку дерева конкретного студента — остальные студенты эту часть SUMMARY не видят.
- Такой подход даёт бонус: весь курс можно хранить/версионировать через **git** (история правок текста заданий, откат изменений, при желании — совместное редактирование через pull request), а не только через БД.
- В БД при этом остаются только "живые" данные: сдачи (`Submission`), статусы, комментарии, привязка студент↔группа — сам текст задания в БД не дублируется, только путь к `.md`-файлу.

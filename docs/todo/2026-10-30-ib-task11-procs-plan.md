## Сюжет

Тема по зерну (магазин / библиотека / клиника), как в №8/№10. На учебном сервере `seclab`
появился посторонний процесс, который грузит CPU, слушает нестандартный порт и **переживает
перезагрузку**. Студент — дежурный Blue Team: по шагам находит процесс, его файл, сетевую
активность, службу и механизм автозапуска, лишнюю учётку/ключ, затем связывает события по времени
и пишет краткий вывод. Явно учим: один признак ≠ взлом; вывод — по совокупности; доказательства не
уничтожать.

Личные данные у каждого студента: тема, имя «вредоносного» процесса и путь к бинарю, PID, порт,
IP «командного центра», имя службы, расписание cron, имя лишней учётки UID 0, отпечаток чужого
SSH-ключа, время событий.

## Что нужно добавить в эмулятор (основная часть работы)

Сейчас в песочнице нет понятия «запущенные процессы», портов и расписаний. Нужна лёгкая модель,
задаваемая генератором в файле песочницы (по аналогии с `owners.json` у №10), например
`var/lib/seclab/procs.json` и `.../sockets.json` (или один файл состояния):

- **Процессы:** список `{pid, ppid, user, cmd, exe, %cpu, %mem, lstart, etime}`. Команды:
  - `ps aux [--sort=-%cpu|-%mem]`, `ps -p PID -o <поля>` (минимум полей из статьи: pid,ppid,user,group,lstart,etime,cmd,args);
  - `/proc/<PID>/exe` как символическая ссылка (чтение `readlink -f`), `/proc/<PID>/cmdline` (для `cat`); каталоги `/proc/<PID>` только для существующих PID из модели;
  - `top` — можно отдать как статичный снимок (не интерактивно) или не реализовывать (оставить `ps`).
- **Сеть:** список сокетов `{proto, state, local, peer, pid, program}`. Команды `ss -lntup`, `ss -tnp`;
  `lsof -i` — опционально (можно не делать в v1, в теории оставить как «если установлен»).
- **systemd:** у `systemctl` уже есть база (`cmd_admin.py`, модель в `var/lib/seclab/*.json`). Добавить
  `list-units --type=service --state=running`, `list-unit-files`, `--failed`, и чтобы `status`/`cat`
  показывали `ExecStart` «вредоносной» службы (unit-файл кладёт генератор в `etc/systemd/system/`).
- **Автозапуск:** `crontab -l` (файл `var/spool/cron/crontabs/<user>`), каталоги `/etc/cron.d|hourly|daily`
  (обычный `ls`/`cat` — уже есть), `systemctl list-timers --all`.
- **Учётки/ключи:** уже есть (`getent passwd`, `/etc/passwd`, `ls -la ~/.ssh`, `cat authorized_keys`).
  Проверку «UID 0, кроме root» разрешить и через `grep`/`awk`. **`awk`** в эмуляторе нет — решить:
  либо добавить минимальный `awk -F: '$3==0{print $1}'` (узкий подкласс), либо в условии предлагать
  `grep ':0:0:'` / `getent passwd | grep`, чтобы не тянуть awk. **Предпочтительно без awk в v1.**
- **journalctl:** есть; убедиться, что `--since`, `-u <служба>` выдают релевантные строки сценария
  (вход по SSH, запуск службы, установка соединения) — их пишет генератор.

> Это самый объёмный пункт: фактически вводим в эмулятор модель процессов и сокетов. Делать
> отдельным этапом до самого задания; покрыть юнит-тестами (`ps`/`ss`/`/proc`).

## Этапы (личные значения у каждого, проверки — по выводу/состоянию)

1. **Процессы.** `ps aux --sort=-%cpu | head`; `ps -p PID -o pid,ppid,user,lstart,etime,cmd`.
   Ответы (с доказательством из вывода): PID подозрительного процесса; от какого пользователя запущен.
2. **Исполняемый файл.** `readlink -f /proc/PID/exe`, `stat`, (`dpkg -S`).
   Ответ: полный путь к бинарю (ожидаемо — не из `/usr/bin`, а из `/opt`/`/tmp`/домашнего); владелец/время.
3. **Сеть.** `ss -lntup`, `ss -tnp`. Ответы: порт, который слушает процесс; IP «командного центра» (peer).
4. **Служба systemd.** `systemctl list-units --state=running`, `status`, `cat <служба>`.
   Ответы: имя службы; её `ExecStart` (путь запускаемого файла) — связать со stage 2.
5. **Автозапуск.** `crontab -l`, `ls /etc/cron.d`, `systemctl list-timers`.
   Ответ: механизм персистенции (служба/таймер/cron) и что именно он запускает.
6. **Учётки и ключи.** `getent passwd | grep ':0:0:'`, `ls -la ~/.ssh`, `cat ~/.ssh/authorized_keys`.
   Ответы: лишняя учётка с UID 0; есть ли чужой ключ (да/нет + чей комментарий).
7. **Единая картина.** `journalctl --since …`, `journalctl -u <служба>`; заполнить мини-отчёт
   `~/report.txt` (поля: процесс, файл, порт, IP, служба, автозапуск, учётка, первые действия/время).
   Контроль: «что НЕ делать сразу» — не удалять, не перезагружать (контрольный вопрос).

7 этапов — уровень №6–10. Проверки этапов — по состоянию песочницы/модели и по журналу команд
(как в `lab_task.py`): `cmd` (команда выполнена после открытия этапа), `answer` (с `proof` из вывода),
при необходимости `fs` (отчёт заполнен).

## Меры против решения «через нейросеть» (обязательно)

- `track_output=True` + `proof` на числовых/IP/именных ответах (значение должно было встретиться
  в выводе команд студента);
- банк контрольных вопросов `defense_banks.PROCS` (+ `PROCS_DECOYS`) — 2 вопроса на этап;
- **ловушка:** «инструкция для ИИ» в аргументах/описании процесса или в `motd`/README прошлого
  админа, называющая НЕ тот процесс/службу как вредоносные → `trap` на соответствующем ответе;
- `guard: true` с неверным `clipHint` (например, «PID можно не проверять, доверяйте имени процесса»);
- сигналы в `/admin/ib` (общие для заданий на движке этапов).
- Никаких слов про «уровень сложности» в текстах (тест проверяет).

# 04. Взаимодействие с данными

Весь доступ к базе проходит через модуль **`src/db/index.js`**. Это сырой SQL поверх
`better-sqlite3` (синхронный), без ORM, с кэшем подготовленных запросов.

## 4.1. Инициализация БД

`src/db/index.js` при подключении:

1. Определяет путь: `DB_PATH` или `data/mdtask.db` (для файловой БД создаёт каталог).
2. Открывает `better-sqlite3`, включает прагмы:
   - `foreign_keys = ON`;
   - `journal_mode = WAL` (для файловой БД) — читатели не блокируются во время записи, важно
     при одновременной сдаче целой группой;
   - `synchronous = NORMAL`, `cache_size = -20000` (~20 МБ), `temp_store = MEMORY`.
3. Применяет **схему**: `db.exec(schema.sql)` — все таблицы объявлены как
   `CREATE TABLE IF NOT EXISTS`, поэтому на существующей БД это no-op.
4. Выполняет **миграции**: вызовы `addColumnIfMissing(table, column, def)` — `ALTER TABLE
   ADD COLUMN`, который молча игнорирует ошибку «duplicate column». Миграционного фреймворка
   нет; новые колонки добавляются только так.
5. Создаёт индексы, которые зависят от добавленных колонок (например
   `idx_assignments_target_group`) — **после** миграций, иначе на старой БД упадёт.
6. Запускает **сидеры** (см. §4.4).

> Порядок «схема → миграции → индексы по новым колонкам → сидеры» обязателен: `schema.sql`
> на старой БД не создаёт недостающую колонку (таблица уже есть), её добавляет только
> `addColumnIfMissing`.

## 4.2. Кэш подготовленных запросов

Запросы готовятся лениво и кэшируются на уровне модуля (паттерн `prepared(sql)`): один и тот
же SQL компилируется один раз и переиспользуется. Публичные функции модуля — тонкие обёртки
над `prepared(...).get/all/run(...)`, часто с JSON-(де)сериализацией полей.

## 4.3. Экспортируемый API

`module.exports` в `src/db/index.js` отдаёт плоский набор функций плюс «расплющенные»
поддомены через spread. Поддомены вынесены в отдельные файлы и собираются фабриками
`make*Db(db, prepared, ...)`:

```js
const examDb        = makeExamDb(...);         // src/db/exam.js
const emmetDb       = makeEmmetDb(...);        // src/db/emmet.js
const htmlCourseDb  = makeHtmlCourseDb(...);   // src/db/html-course.js
const cssCourseDb   = makeCssCourseDb(...);    // src/db/css-course.js
const linuxCourseDb = makeLinuxCourseDb(...);  // src/db/linux-course.js
const jsCourseDb    = makeJsCourseDb(...);     // src/db/js-course.js
const pythonCourseDb= makePythonCourseDb(...); // src/db/python-course.js
const topicLocksDb  = makeTopicLocksDb(...);   // src/db/topic-locks.js

module.exports = {
  getUsers, verifyUserCredentials, getUserById, createUser, setUserPassword, ...
  getCourses, getAssignments, getAssignmentsForStudent, getSubmissions,
  reviewSubmission, createSubmission, getLatestSubmission, createAssignment, ...
  getSqlExercises, createSqlAttempt, getAllSqlAttempts, getSolvedSqlExerciseIds, ...
  getCaesarSecrets, getConfigTasks, getTerminalTasks, getLabTasks, getLabLog,
  getIbGuardCounts, getIbGuardEvents, getIbTaskDefense, ...
  getSession, setSession, touchSession, destroySession, purgeExpiredSessions,
  ...examDb, ...emmetDb, ...htmlCourseDb, ...cssCourseDb, ...linuxCourseDb,
  ...jsCourseDb, ...pythonCourseDb, ...topicLocksDb,
  __resetForTests,
};
```

Так вызывающий код делает `require('../db')` и зовёт нужную функцию, не зная, в каком файле
она определена.

Примеры функций замков тем (`topicLocksDb`): `getTopicOverride`, `listTopicOverrides(subject?)`,
`topicOverridesForStudent(subject, group, studentId)`, `setTopicOverride(...)`,
`clearTopicOverride(...)`.

## 4.4. Сидеры

- `seed.js` — наполняет **только пустую** БД (учётки, курсы и т.п.).
- `seedSqlExercises` / `seedLanguageExercises` — идут `INSERT OR IGNORE` на **каждом** старте,
  поэтому новые упражнения доезжают до существующих БД. **Существующие строки упражнений не
  обновляются**: если изменить уже засеянное упражнение, реальная БД сохранит старую строку,
  пока его явно не мигрировать. `seedSqlExercises` также выравнивает `order_index` по данным
  (`syncOrderIndexes`), чтобы упражнения можно было вставлять в середину цепочки.

## 4.6. Как компоненты взаимодействуют с данными

- **Роуты не трогают БД напрямую через SQL** — только через функции `src/db`.
- **Админка** агрегирует в памяти: `admin-data.loadContext()` разово читает users/courses/
  assignments/submissions и строит индексы (`*ById`, `latestByPair`, `works`); остальные
  функции (`dashboard`, `assignmentRows`, `studentProfile`, `trainerMatrix`, `ibResults`…)
  считают по этому контексту. Это держит всю «логику статусов» в одном тестируемом месте.
- **Предметы-тренажёры**: клиент выполняет задачу в браузере → шлёт результат в API предмета
  → сервер **перепроверяет** (валидаторы в `src/lib/*`) и пишет прогресс/событие. Сервер
  студенческий код не исполняет (Pyodide/воркеры — в браузере).
- **JSON-в-колонках**: статистика прогресса, параметры/прогресс заданий ИБ, варианты
  контрольных, файлы сдач — хранятся как JSON-текст и (де)сериализуются обёртками `src/db`.
  Наивная строковая замена по таким полям ломает экранирование — менять через JSON.parse/
  stringify.

## 4.7. Реальные данные, бэкапы, тестовый режим

- `data/mdtask.db`, `data/trainer/`, `data/ctf/`, `data/exam/` и `uploads/` — **реальные**
  аккаунты и работы. **Никогда** не удалять и не сбрасывать. `backups/` — ручные снимки.
- **Тесты** всегда идут на `DB_PATH=:memory:` и временных каталогах (их задаёт `npm test`).
  `db.__resetForTests()` (в `beforeEach`) удаляет все строки и пере-сеет базовых пользователей
  `student-1..8` + `teacher-1` — в тестах нужно брать **непересекающиеся** id, иначе
  `UNIQUE constraint failed: users.id`.
- **WAL-нюанс:** копировать `.db` без его `-wal`-файла — потерять свежие данные. Для
  консистентной копии: `sqlite3 src ".backup dst"`. Перед изменениями БД — делать бэкап.
- Для UI-проверок на «фейковых» данных — копировать БД в сторону и поднимать второй инстанс
  на другом порту с `DB_PATH`/`UPLOAD_DIR`/`TRAINER_DB_DIR` на копию.

## 4.8. Скрипты обслуживания данных (примеры)

- `scripts/fixes/*` — точечные правки прод-данных (идемпотентные, с бэкапом БД): перегруппировка,
  добавление групп/аккаунтов, пометка задания выполненным.
- `scripts/exam/*` — выдача/пересборка вариантов, импорт ПК аудитории, перепроверка после
  контрольной.
- Серверное обновление трогает только код и сохраняет `data/`.

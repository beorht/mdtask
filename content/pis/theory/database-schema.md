# Как рисовать схему базы данных

Схема базы данных (модель данных) показывает, **какие данные хранит система и как они связаны**. По ней потом создают таблицы. Ошибку, найденную на схеме, исправить легко. Ту же ошибку в базе, заполненной данными, исправлять долго и дорого.

Схему строят в три шага:

1. найти **сущности** предметной области (что мы храним);
2. описать их **атрибуты** и **ключи** (какие сведения о каждой сущности);
3. провести **связи** между сущностями и указать их **кратность** (сколько с чем связано).

Сквозной пример — информационная система «Библиотека».

## 1. Сущности и атрибуты

**Сущность** — класс однотипных объектов, о которых система хранит данные: «Книга», «Читатель», «Автор», «Выдача». В базе данных каждая сущность становится **таблицей**, а каждый конкретный объект — **строкой** этой таблицы.

**Атрибут** — свойство сущности: название книги, ФИО читателя, дата выдачи. Атрибут становится **столбцом** таблицы.

Как находить сущности: выпишите **существительные** из описания задачи. Например: «Читатель берёт **книгу**, библиотекарь оформляет **выдачу**, у книги есть **автор**». Существительные, у которых много своих свойств, — это сущности («Читатель»). Существительные, которые просто описывают что-то другое, — это атрибуты («дата выдачи»).

**Ключи:**

| Ключ | Что это | Пример |
|---|---|---|
| **Первичный ключ** (PK, primary key) | атрибут, который однозначно определяет строку; не повторяется, не бывает пустым; на схеме подчёркнут | `id_книги` |
| **Внешний ключ** (FK, foreign key) | атрибут, который ссылается на первичный ключ другой сущности, — так записывается связь | `id_автора` в таблице «Книга» |

## 2. Нотация ER: «сущность — связь»

Классическая ER-диаграмма (Entity–Relationship, модель Чена) изображает сущности прямоугольниками, атрибуты — овалами, связи — ромбами:

![ER-диаграмма](/img/pis/erd.png)

*ER-диаграмма: сущности (прямоугольники), атрибуты (овалы, ключевой атрибут подчёркнут), связи (ромбы) с кратностью 1, M, N. Жирная рамка — «слабая» сущность, которая не существует без другой*

На практике для баз данных чаще рисуют **табличную** схему: каждая сущность — прямоугольник со списком полей, связи — линии между ключами. Такую схему удобно рисовать в draw.io и сразу переносить в SQL (см. раздел 6).

## 3. Нотация UML: диаграмма классов

В UML сущность изображается **классом**: прямоугольник из трёх секций.

![Класс «Формуляр книги»](/img/pis/class-book-form.png)

*Класс «Формуляр книги»: сверху стереотип `<<регистр учета>>` и имя, в середине атрибуты с типами (подчёркнутый `id_Экземпляра` — ключ), снизу операции «Выдать», «Принять», «Забронировать»*

| Секция | Что пишут | Пример |
|---|---|---|
| имя | название сущности (и стереотип в `<< >>`) | `Формуляр книги` |
| атрибуты | `- имя : тип` | `- Год публикации : Date` |
| операции | `+ действие() : результат` | `+ Выдать() : Boolean` |

Для схемы базы данных обычно хватает имени и атрибутов. Операции нужны, когда проектируют классы программы.

### Виды отношений

| Отношение | Как рисуется | Смысл | Пример |
|---|---|---|---|
| **Ассоциация** | сплошная линия (можно со стрелкой и подписью) | объекты связаны | автор **написал** книгу |
| **Зависимость** | пунктирная стрелка | изменение одного влияет на другой | запись о выдаче меняет статус книги |
| **Обобщение** (наследование) | линия с **пустым треугольником** у общего класса | «частное — это разновидность общего» | Проза, Стихи, Басни → Произведение |
| **Агрегация** | линия с **пустым ромбом** у целого | «часть — целое», части живут сами по себе | библиотека и её книги |
| **Композиция** | линия с **закрашенным ромбом** у целого | части не существуют без целого | книга и её переплёт, корешок, форзац |

![Рефлексивная ассоциация](/img/pis/rel-association-reflexive.png)

![Обобщение](/img/pis/rel-generalization.png)

*Обобщение: Проза, Стихи, Басни и другие — разновидности «Произведения»*

![Агрегация](/img/pis/rel-aggregation.png)

*Агрегация: часть может существовать отдельно от целого*

*Композиция: переплёт, корешок, форзац, каптал, авантитул не существуют без книги*

## 4. Связи и кратность

**Кратность** показывает, сколько объектов одной сущности связано с одним объектом другой. Её пишут у концов линии:

| Запись | Значит |
|---|---|
| `1` | ровно один |
| `0..1` | ни одного или один (связь необязательна) |
| `1..*` | один или больше |
| `0..*` или `*` | любое количество, в том числе ни одного |

Три основных вида связи:

### Один к одному (1:1)

![Связь 1:1](/img/pis/link-1-1.png)

*У каждого экземпляра книги одна учётная карточка, и у каждой карточки один экземпляр*

В таблицах: внешний ключ ставят в одну из таблиц и делают его **уникальным**. Связь 1:1 встречается редко. Часто такие сущности можно объединить в одну.

### Один ко многим (1:M)

![Связь 1:M](/img/pis/link-1-m.png)

*Один автор написал много книг (`1..*`), у книги в этой модели один автор (`0..1`)*

Самая частая связь. В таблицах: **внешний ключ ставят на стороне «многие»**. В таблице «Книга» есть поле `id_автора`, которое ссылается на «Автора».

### Многие ко многим (M:M)

![Связь M:M](/img/pis/link-m-m.png)

*Читатель берёт много книг, и книгу берут много читателей. Связь раскрыта через сущность «Записи формуляра» — каждая запись хранит одну операцию: кто, какую книгу, когда*

В реляционной базе связь M:M **напрямую не хранится**. Её раскрывают через **связующую таблицу** с двумя внешними ключами:

```
Читатель (id_читателя PK, ФИО, телефон)
Книга    (id_книги PK, название, год)
Выдача   (id_выдачи PK, id_читателя FK, id_книги FK, дата_выдачи, дата_возврата)
```

Связующая таблица часто сама оказывается полезной сущностью со своими атрибутами (дата выдачи, дата возврата).

## 5. Нормализация и декомпозиция

**Нормализация** — правила, которые убирают дублирование данных и противоречия. Для учебных схем достаточно трёх нормальных форм:

| Форма | Правило | Нарушение | Как исправить |
|---|---|---|---|
| **1NF** | в каждой ячейке одно значение, нет повторяющихся групп столбцов | поле `телефоны: "123, 456"`, столбцы `книга1, книга2, книга3` | отдельная таблица «Телефон» / «Выдача» |
| **2NF** | 1NF + каждый неключевой атрибут зависит от **всего** составного ключа | в «Выдаче» с ключом (читатель, книга) хранится `название_книги` | название — в таблице «Книга» |
| **3NF** | 2NF + неключевые атрибуты не зависят друг от друга | в «Книге» хранятся `id_автора` **и** `ФИО_автора` | ФИО — только в таблице «Автор» |

Правило для запоминания: **каждый факт хранится в одном месте**. Если, изменив ФИО автора, нужно править сотню строк, схема не нормализована.

**Декомпозиция.** Одну «толстую» сущность, в которой смешаны сведения разного рода, делят на несколько. Хороший признак для деления: **события, которые меняют атрибуты**. Название и автор книги не меняются никогда. Место хранения меняется при перестановке. Выдача происходит постоянно. Значит, это разные сущности:

![Пример декомпозиции](/img/pis/decomposition.png)

*Слева — одна сущность «Издание», где смешано всё: название, регистрационный номер, дата выдачи, последний читатель, статус. Справа — та же предметная область после декомпозиции: Автор, Книга, Формуляр книги (экземпляр), Место хранения, Читатель, Записи формуляра, Статус — со связями и кратностями*

Не увлекайтесь: слишком мелкое дробление делает схему трудной для понимания. Делите, когда части меняются по разным причинам или в разное время.

## 6. Как нарисовать схему базы данных

**Порядок работы:**

1. Выпишите сущности (существительные из описания).
2. Для каждой выпишите атрибуты и выберите первичный ключ (обычно `id`).
3. Для каждой пары связанных сущностей ответьте на два вопроса: «сколько B у одного A?» и «сколько A у одного B?». Так получится 1:1, 1:M или M:M.
4. Для 1:M поставьте внешний ключ на сторону «многие». Для M:M добавьте связующую таблицу.
5. Проверьте 1NF–3NF: нет ли списков в одной ячейке и одинаковых данных в разных таблицах.
6. Подпишите связи и кратности.

**Инструменты:**

| Инструмент | Как |
|---|---|
| **draw.io** (app.diagrams.net) | «+ Ещё фигуры» → включить **Entity Relation** (таблицы со строками полей и линии «вороньи лапки» для кратности) или **UML** (классы) |
| **MS Word / PowerPoint / Visio** | таблица или прямоугольник со списком полей на каждую сущность, соединители-стрелки с подписями `1` и `*`; в Visio — шаблон «Схема базы данных» / «Схема классов UML» |
| **Paint или от руки** | прямоугольник = таблица, внутри поля (PK подчеркнуть, FK пометить), линии со значками кратности |

В нотации «вороньи лапки» (Crow's Foot), которую использует draw.io, кратность рисуется на конце линии: черта `|` — «один», кружок `o` — «ноль» (необязательно), «лапка» с тремя линиями — «много». Например, `||——o<` значит «ровно один — ноль или много».

**Пример готовой табличной схемы «Библиотеки»:**

```
┌──────────────┐        ┌──────────────────┐        ┌───────────────┐
│ Автор        │        │ Книга            │        │ Читатель      │
├──────────────┤ 1    * ├──────────────────┤        ├───────────────┤
│ PK id_автора │────────│ PK id_книги      │        │ PK id_читателя│
│    ФИО       │        │    название      │        │    ФИО        │
└──────────────┘        │ FK id_автора     │        │    телефон    │
                        └──────────────────┘        └───────────────┘
                                 │ 1                        │ 1
                                 │                          │
                                 │ *   ┌────────────────┐ * │
                                 └─────│ Выдача         │───┘
                                       ├────────────────┤
                                       │ PK id_выдачи   │
                                       │ FK id_книги    │
                                       │ FK id_читателя │
                                       │    дата_выдачи │
                                       │    дата_возврата│
                                       └────────────────┘
```

Та же схема на SQL. По хорошей схеме таблицы пишутся почти механически:

```sql
CREATE TABLE authors (id INTEGER PRIMARY KEY, full_name TEXT NOT NULL);
CREATE TABLE books   (id INTEGER PRIMARY KEY, title TEXT NOT NULL,
                      author_id INTEGER REFERENCES authors(id));
CREATE TABLE readers (id INTEGER PRIMARY KEY, full_name TEXT NOT NULL, phone TEXT);
CREATE TABLE loans   (id INTEGER PRIMARY KEY,
                      book_id INTEGER NOT NULL REFERENCES books(id),
                      reader_id INTEGER NOT NULL REFERENCES readers(id),
                      issued_at TEXT NOT NULL, returned_at TEXT);
```

## 7. Типичные ошибки

| Ошибка | Как правильно |
|---|---|
| нет первичного ключа | у каждой таблицы есть PK (`id`) |
| M:M нарисована одной линией между двумя таблицами | добавьте связующую таблицу с двумя FK |
| внешний ключ на стороне «один» (в «Авторе» поле `id_книги`) | FK — на стороне «многие»: в «Книге» поле `id_автора` |
| список в одной ячейке (`книги: "1, 5, 7"`) | отдельная строка на каждое значение (1NF) |
| одни и те же данные в нескольких таблицах (ФИО автора в «Книге») | храните факт в одном месте, ссылайтесь ключом (3NF) |
| связи без кратности | подпишите `1`, `0..1`, `*` или используйте «вороньи лапки» |

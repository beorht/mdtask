# №6. Расследование инцидента по журналам

Задание сделано по сценарию «Миссия 5. Реагирование на инцидент» (`data/TermialEmulatorScenariy/`).

## Цель

Научить студентов разбирать журналы входа Linux, отличать подбор пароля от «шума» и опечаток,
сохранять доказательства (копия + SHA-256), строить временную шкалу, отделять факты от
гипотез, принимать соразмерные меры (блокировка, а не удаление) и оформлять отчёт.

Задание выполняется в веб-терминале: «Информационная безопасность» → «Задание №6».
Перед практикой студент читает теорию `ib/ctf/incident/THEORY.md`.

## Что получает студент

Свой учебный сервер `data/ctf/incident/<student_id>/` (в терминале — `/`), у каждого свой инцидент:

| Где | Что |
|---|---|
| `/var/log/auth.log` (640, только sudo) | двое суток: CRON, обычные входы `admin` и сотрудника, одна опечатка `admin`, ночной перебор несуществующих имён со «сканера» (`198.51.100.x`), затем серия неудачных попыток к **существующей** учётной записи с `203.0.113.x`, успешный вход и `sudo chmod` внутреннего отчёта |
| `/var/log/wtmp`, `/var/log/btmp` | сеансы (`last`) и неудачные входы (`sudo lastb`) |
| `/etc/passwd`, `/etc/shadow`, `/etc/group` | атакованный сотрудник по ошибке состоит в группе `sudo` |
| `/etc/sudoers.d/web-maintainers` | какие права ему на самом деле положены |
| `/srv/company/reports/` | отчёт, которому злоумышленник поставил права 666/664/646 |
| `~/incident/report-template.txt` | заготовка отчёта |

Личные значения (учётная запись, IP, число попыток, время входа, файл, права) видны
преподавателю в `/admin/ib` (колонка «Значения») и лежат в `ib_lab_tasks.params`.

## Этапы и проверка

| № | Этап | Как засчитывается |
|---|---|---|
| 1 | Первичный осмотр журналов | `ls -l /var/log`, чтение `auth.log` через sudo, ответы 1.1 (строк), 1.2 (время последней записи) |
| 2 | Сохранение доказательств | `~/evidence/auth.log` совпадает с оригиналом, `~/evidence/auth.log.sha256` содержит его SHA-256 |
| 3 | Неудачные попытки входа | ответы: всего `Failed password`, IP атакующего, учётная запись, число попыток |
| 4 | Успешный вход и действия | ответы: время входа, файл, установленные права, группа `sudo` |
| 5 | Временная шкала | `~/incident/timeline.txt` = все строки с IP атакующего, `~/incident/sudo.txt` = все команды sudo этой учётной записи (в исходном порядке) |
| 6 | Факты и гипотезы | вход был — да; доказательство вывоза данных — нет; ошибок `admin` — 1 |
| 7 | Сдерживание | учётная запись заблокирована (`!` в shadow или nologin), удалена из `sudo`, файлу возвращены права 640 |
| 8 | Отчёт | поля `~/incident/report.txt`: учётная запись, IP, число попыток, время входа, путь файла, меры |

**Критические пункты** (проверяются после каждой изменившей что-то команды, с предупреждением
в терминале; этап с ними не засчитывается, пока нарушено):
- `/var/log/auth.log` не изменён (SHA-256 из генератора);
- `admin` и сам студент не заблокированы и остаются в `sudo`.

## Выдача и проверка

```bash
python3 ib/ctf/incident/generate_incident.py --group IB          # выдать группе
python3 ib/ctf/incident/generate_incident.py --student ID        # одному студенту
python3 ib/ctf/incident/generate_incident.py --student ID --force # выдать заново (прогресс обнуляется)
python3 ib/ctf/incident/generate_incident.py --group IB --refresh-task  # переписать ~/TASK.md
python3 ib/checks/lab_check.py --task incident ID --text          # подробно по студенту
python3 ib/checks/lab_check.py --task incident --group IB --update-db
```

Если студент испортил журнал, выдайте задание заново с `--force`. Прогресс при этом обнуляется.

# №7. Безопасный удалённый доступ по SSH

Задание сделано по сценарию «Миссия 3. Безопасный удалённый доступ» (`data/TermialEmulatorScenariy/`).

## Цель

Научить студентов проводить аудит конфигурации SSH, понимать, какое значение параметра
действует (Include, первое значение), настраивать вход по ключу (`authorized_keys`, права,
StrictModes), ограничивать круг пользователей, проверять (`sshd -t`) и применять (`systemctl reload`)
конфигурацию, не теряя собственный доступ, и планировать откат.

Задание выполняется в веб-терминале: «Информационная безопасность» → «Задание №7».
Перед практикой студент читает теорию `ib/ctf/ssh/THEORY.md`.

## Что получает студент

Свой учебный сервер `data/ctf/ssh/<student_id>/` (в терминале — `/`):

| Где | Что |
|---|---|
| `/etc/ssh/sshd_config` | личный порт, `PermitRootLogin yes`, `PermitEmptyPasswords yes`, `MaxAuthTries 10`, нет `AllowGroups`; в начале `Include /etc/ssh/sshd_config.d/*.conf` |
| `/etc/ssh/sshd_config.d/50-cloud-init.conf` | `PasswordAuthentication yes`: действует раньше основного файла (ловушка) |
| `/etc/ssh/ssh_config` | конфигурация **клиента** (ловушка: на сервер не влияет) |
| учётные записи | студент (`sudo`, `sshadmins`), `deploy` (`sshadmins`, входит по своему ключу), `intern` (пароль, `/bin/bash`, не должен входить), `root` с паролем |
| `~/.ssh` | `id_ed25519`, `id_ed25519.pub`; каталог с правами 775 (StrictModes отвергнет ключ), `authorized_keys` нет |
| `/var/lib/seclab/sshd.json` | «работающая» служба: настройки применяются только через `systemctl reload/restart` |

## Как устроена модель SSH

- `server/sshd_sim.py` читает `sshd_config` как sshd: `Include` в начале, первое значение
  параметра, `Allow*`/`Deny*` накапливаются; ошибки выводятся в формате `sshd -t`.
- `systemctl reload ssh` при ошибке оставляет старые настройки, `restart` при ошибке
  **останавливает** службу (`Connection refused`), `start` запускает снова.
- `ssh [-i ключ] [-p порт] [-o PubkeyAuthentication=no] user@localhost` проверяет вход по
  **работающим** настройкам: DenyUsers/AllowUsers/DenyGroups/AllowGroups, PermitRootLogin,
  StrictModes (права каталога `.ssh` и `authorized_keys`), ключи, PasswordAuthentication.
  Ключ пробуется первым, затем пароль (эмулятор «вводит» его сам). Причины отказов
  пишутся в `/var/log/auth.log`.
- Ключи учебные: открытый ключ выводится из закрытого хешем, так что пара всегда согласована.

## Этапы и проверка

| № | Этап | Как засчитывается |
|---|---|---|
| 1 | Аудит службы SSH | `systemctl status ssh`, `sudo sshd -T`; ответы: порт, `PermitRootLogin` (yes), файл с действующим `PasswordAuthentication` |
| 2 | Учётные записи и группы | `getent group sshadmins`; ответы: 2 участника, `intern` |
| 3 | Резервная копия | `/etc/ssh.bak/sshd_config` и `/etc/ssh.bak/sshd_config.d/50-cloud-init.conf` совпадают с исходными |
| 4 | Вход по ключу | ключ в `~/.ssh/authorized_keys`, права 700/600, успешный `ssh` по ключу |
| 5 | Ужесточение | действующие значения: `PermitRootLogin no`, `PasswordAuthentication no`, `PermitEmptyPasswords no`, `MaxAuthTries ≤ 3`, политика пускает студента и `deploy`, но не `intern`; без ошибок |
| 6 | Проверка и применение | `sudo sshd -t`, `sudo systemctl reload ssh`, служба работает с конфигурацией из файлов |
| 7 | Проверка доступа | вход по ключу — успех; `-o PubkeyAuthentication=no`, `root`, `intern` — отказ |

**Критический пункт** (с этапа 6): студент может войти по ключу по работающей конфигурации.
Если служба остановлена или студент запер сам себя, терминал предупреждает, и этап не засчитывается.

# №2. Контейнерная изоляция студенческих сессий

Цель: каждый студент получает свою изолированную среду (контейнер) для выполнения лабораторных работ, без возможности повлиять на хост-систему или на сессии других студентов. Это следующий слой после [[№1.SSH-key-only-auth]] — ключ пускает студента внутрь, а контейнер ограничивает, что он может сделать оказавшись там.

## Этап 1. Выбор технологии изоляции

| Вариант | Плюсы | Минусы |
|---|---|---|
| Docker + namespaces/cgroups | просто, быстро, огромная экосистема образов | ядро общее с хостом — слабее изоляция для рискованных лаб (privesc, kernel exploits) |
| Firecracker microVM | настоящая VM-изоляция, лёгкая и быстрая | сложнее в оркестрации, нужен свой API-слой |
| gVisor (runsc) поверх Docker | усиленная изоляция syscall'ов при простоте Docker | небольшой прирост латентности, не 100% совместимость со всеми syscalls |

**Рекомендация для MVP:** начать с Docker + строгие ограничения (ниже), для модулей с privilege escalation/эксплойтами ядра — добавить Firecracker или gVisor как runtime класс "повышенной изоляции".

## Этап 2. Базовый образ лабораторной среды

```dockerfile
FROM debian:12-slim

RUN apt-get update && apt-get install -y --no-install-recommends \
    openssh-server sudo vim nano curl net-tools iproute2 \
    && rm -rf /var/lib/apt/lists/*

RUN useradd -m -s /bin/bash student \
    && mkdir -p /home/student/.ssh \
    && chmod 700 /home/student/.ssh

COPY authorized_keys /home/student/.ssh/authorized_keys
RUN chmod 600 /home/student/.ssh/authorized_keys \
    && chown -R student:student /home/student/.ssh

COPY sshd_config /etc/ssh/sshd_config
EXPOSE 22
CMD ["/usr/sbin/sshd", "-D"]
```

`sshd_config` внутри образа — тот же файл, что настроили в задании №1 (только ключ, без пароля).

## Этап 3. Ограничение ресурсов (cgroups)

```bash
docker run -d \
  --name lab-student42 \
  --cpus="1" \
  --memory="512m" \
  --pids-limit=100 \
  --restart=no \
  lab-image
```
- `--cpus` / `--memory` — не дают одному студенту забрать ресурсы хоста
- `--pids-limit` — защита от fork-бомб

## Этап 4. Сетевая изоляция

```bash
docker network create --internal lab-net-student42
docker run -d --network lab-net-student42 --name lab-student42 lab-image
```
- `--internal` — контейнер без выхода в интернет по умолчанию
- Отдельная сеть на студента (или изолированный сегмент на группу), чтобы лабораторные по сканированию/MITM не задевали чужие контейнеры
- Для сетевых лабораторий (nmap, ARP spoofing) — создавать отдельную "полигонную" сеть с несколькими подставными хостами-мишенями внутри неё

## Этап 5. Снижение привилегий контейнера

```bash
docker run -d \
  --cap-drop=ALL \
  --cap-add=NET_RAW \
  --security-opt=no-new-privileges \
  --security-opt seccomp=./seccomp-lab.json \
  --read-only \
  --tmpfs /tmp \
  --tmpfs /home/student:size=256m,exec \
  lab-image
```
- `--cap-drop=ALL` + точечный `--cap-add` (например `NET_RAW` для tcpdump/nmap-лаб) — минимально необходимые права
- `no-new-privileges` — блокирует эскалацию через SUID-бинарники внутри контейнера
- `--read-only` + `tmpfs` под `/home/student` — файловая система только для чтения, кроме рабочей директории студента
- Свой `seccomp` профиль — сузить набор разрешённых syscalls под конкретный тип лабораторной (например, для web-лаб не нужен `ptrace`)

## Этап 6. Проброс SSH к контейнеру

Два варианта:
1. **Проброс портов**: `-p 2201:22` — каждому контейнеру свой порт на хосте (просто, но плохо масштабируется)
2. **SSH-бастион + `AuthorizedKeysCommand`**: один входной sshd на хосте, который по ключу студента определяет его контейнер и делает `ProxyJump`/forced command внутрь — лучше для платформы с сотнями студентов

Рекомендация: начать с варианта 1 для MVP, перейти на вариант 2 при масштабировании.

## Этап 7. Жизненный цикл контейнера (оркестрация)

- Скрипт/сервис, который на вход сессии в веб-терминале:
  1. Создаёт контейнер из нужного образа лабораторной работы
  2. Кладёт публичный ключ студента в `authorized_keys`
  3. Возвращает адрес/порт веб-терминалу для подключения
- На выход/таймаут сессии — контейнер уничтожается (`docker rm -f`), никакого сохранения состояния между попытками (если это не противоречит цели лабораторной)

## Этап 8. Логирование и мониторинг инцидентов

- Логи sshd и команд студента (auditd или `script`/shell-логирование) — для последующей проверки хода выполнения работы
- Ограничение времени жизни сессии (таймаут), чтобы забытые контейнеры не копились
- Алерты при аномальной нагрузке (возможный побег из песочницы или атака на хост)

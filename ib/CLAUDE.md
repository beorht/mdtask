# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

IBEmulator is a browser-based terminal emulator for practical labs in an Information Security course: a web terminal backed by real student data, lab tasks, and automated checkers. All user-facing text (UI strings, command output, task files, docs, comments) is in Russian — keep it that way.

There are no dependencies, no build step and no linter; `tests/` holds a stdlib unittest suite for the shell emulator and tasks №4–5. Backend is pure Python 3 stdlib; frontend is plain HTML/CSS/JS in single files.

## Commands

```bash
# Run the terminal backend (http://localhost:8088, terminal at /prototype/terminal-lab.html, admin at /admin-panel/index.html)
python3 server/app.py
MDTASK_DB=/path/to/mdtask.db CTF_CAESAR_DIR=/path/to/sandboxes PORT=8088 python3 server/app.py

# Generate task №3 (Caesar) secrets + sandboxes for a student group
python3 ctf/caesar-secret/generate_challenge.py --group IB [--db ...] [--out ...] [--force]
# Generate task №4 (config files: find/grep/sed) sandboxes; check them
python3 ctf/configs/generate_configs.py --group IB | --student ID [--db ...] [--out ...] [--force | --refresh-task]
python3 checks/task4_check.py <student_id> [--text] | --group IB [--update-db] | --all
# Generate task №5 (terminal basics trainer) sandboxes; check them
python3 ctf/terminal/generate_terminal.py --group IB | --student ID [--db ...] [--out ...] [--force | --refresh-task | --repair]
python3 checks/task5_check.py <student_id> [--text] | --group IB [--update-db] | --all
# Generate tasks №6 (incident response) / №7 (secure SSH) sandboxes; check them
python3 ctf/incident/generate_incident.py --group IB | --student ID [--db ...] [--out ...] [--force | --refresh-task]
python3 ctf/ssh/generate_ssh.py --group IB | --student ID [--force | --refresh-task]
python3 ctf/logs/generate_logs.py --group IB | --student ID [--force | --refresh-task]   # task №8
python3 ctf/grep/generate_grep.py --group IB | --student ID [--force | --refresh-task]   # task №9 (+ data/ctf/grep-check/<id>/)
python3 ctf/perms/generate_perms.py --group IB | --student ID [--force | --refresh-task]  # task №10
python3 checks/lab_check.py --task incident|ssh|logs|grep|perms <student_id> [--text] | --group IB [--update-db] | --all

# Tests (stdlib unittest, temp dirs only; also run by mdtask's `npm test`)
python3 -m unittest discover -s tests

# Run checkers
checks/task1_check.sh <student_id> <host> <user> <identity_file> [port]
checks/task2_check.sh <student_id> <container_name>
checks/run_all.py checks/students.example.json > checks/reports/report.json
```

## Architecture

**Part of mdtask.** IBEmulator now lives inside mdtask as `ib/` (the "Информационная безопасность" subject). It reads and writes mdtask's SQLite DB (default `<mdtask>/data/mdtask.db`, computed from the file location) and reads student sandboxes from `<mdtask>/data/ctf/caesar/<student_id>/`. Inside mdtask, `server/bridge.py` runs `handle_api()` from `app.py` for Node (`src/lib/ib-bridge.js`, JSON lines over stdin/stdout); `src/routes/ib.js` serves `prototype/terminal-lab.html` with `window.SECLAB_API` set and forwards `/ib/<task>/api/*`, allowing the TTY login only for the logged-in mdtask student. The standalone `app.py` server still works the same way. The `users` table belongs to mdtask; IBEmulator only adds `ctf_caesar_secrets` (schema in `ctf/caesar-secret/schema.sql`, also created inline by the generator). Running the generator or unlocking the task DB (which sets `solved`) mutates that real DB.

**Terminal flow (`prototype/terminal-lab.html` ↔ `server/app.py`).**
- `POST /api/login` checks the primary password first (`users.password_hash/password_salt`, scrypt n=16384 r=8 p=1 dklen=64, with the salt used as raw UTF-8 bytes — must stay byte-compatible with mdtask's `src/lib/password.js`). The task №3 password is *not* accepted for login.
- `POST /api/login` also takes `task` (`caesar` — default, `configs`, `terminal`); it picks the session's sandbox (`make_sandbox()`): task №3 — `data/ctf/caesar/<id>/` shown as the read-only home `/home/<id>`; tasks №4/№5 — `data/ctf/configs/<id>/` / `data/ctf/terminal/<id>/` shown as a whole system `/` with home `/home/<id>`.
- `POST /api/complete {line}` is Tab completion (`shell.complete()`: command names in command position, otherwise paths).
- `POST /api/run {cmd}` goes through `run_line()`. If the session has an open sqlite3 shell, the line is fed to it; otherwise `shell.run()` interprets it (no subprocesses): `server/shell.py` is a bash emulator (tokenizer with quotes/`$VAR`/`$(...)`/globs, `| ; && ||`, redirections `> >> < 2> 2>&1 &>`, simple commands), `cmd_find.py` / `cmd_grep.py` / `cmd_sed.py` implement GNU find/grep/sed, `cmd_files.py` implements mkdir/rmdir/rm/mv/cp/chmod/ln/readlink/file/basename/dirname/tree, `posixre.py` translates BRE/ERE to Python `re`, `manpages.py` holds `man` pages. Commands get a `Ctx` (session, sandbox, `priv` for sudo) and an `IO` (stdin text, out/err sinks). `Ctx.run_argv` records every executed command in `ctx.trace` (argv, cwd before/after, status, priv, nesting depth), which task №5 checks against. A command name containing `/` runs a script from the sandbox (needs the x bit; `bash file` does not), line by line through the same emulator. `run_line()` expands history (`!!`, `!N`, `!-N`, `!prefix`) via `shell.expand_history()` before running and echoes the expanded line; history lives in `session["history"]` (task №5 preloads it from `ib_terminal_log`). Output `__CLEAR__` is a sentinel that the handler turns into `{clear: true}`. Responses carry `nextPrompt` (full prompt text) and `mode` (`shell`/`sqlite`); the frontend renders the prompt as given and only intercepts `logout`/`exit` in `shell` mode. `{interrupt: true}` (Ctrl+C) clears a pending multi-line SQL statement.
- Sessions live in the in-process `SESSIONS` dict (cookie `sid`) and are lost on restart; each session tracks `cwd` relative to the sandbox root and an optional `SqliteShell`.
- `server/sqlite_shell.py` is a simplified emulation of the `sqlite3` CLI. It's an emulator, so it covers the common cases rather than aiming for full CLI parity. SQL runs on the real SQLite engine; dot-commands and output modes (box/table/markdown/...) are implemented by hand. Sandbox safety relies on: DB paths resolved via `db_path_resolver()` in `app.py`, an authorizer that denies ATTACH/DETACH (this also blocks `VACUUM INTO`) and some PRAGMAs, `max_page_count`, and a progress-handler timeout.
- Task №3 goal: open the password-protected DB `~/Documents/backup/company_data.db`. `server/protected_db.py` defines its educational encryption format (MAGIC header + salt, XOR with a SHAKE-256 stream keyed by scrypt). The generator imports the same module via `sys.path` so the format stays shared. `sqlite3 <protected file>` returns a `PasswordPrompt` state (mode `password`: the frontend masks input and skips history, and the server blanks `cmd` in the response). A correct password deserializes the DB into memory (changes are not persisted) and calls `mark_solved()`. `.open` refuses protected files.
- Every path goes through `vfs.Sandbox.resolve()`: lexical normalisation plus a realpath check that symlinks don't leave the sandbox (path-traversal protection). `Sandbox` also emulates ownership and permissions: everything under the home dir belongs to the student, the rest to root; reading root files without the "others read" bit and any write outside home need `sudo` (modes come from the real file modes the generator sets). Redirections are performed by the shell without sudo, as in bash. Task №3's sandbox is read-only (`writable=False`). `sed -i` on a symlink replaces it with a regular file unless `--follow-symlinks`, like GNU sed. Creating or removing entries needs owner write permission on the directory (`check_dir_write`). `rm`/`mv` refuse `/`, the home dir and its ancestors even with sudo (`Sandbox.protected`). `ln -s` with an absolute target stores the real in-sandbox path on disk, and `Sandbox.readlink()` maps it back to the virtual path. New files are created 0644, new dirs 0755.

**Task №3 generator (`ctf/caesar-secret/generate_challenge.py`).** Per student: random password (word + 3 digits), Caesar shift 2–25, and a hidden file path drawn without repetition from `HIDDEN_NAME_POOL` (built from `HIDDEN_DIRS`, 100+ paths; paths already held by students not being regenerated are excluded). Every *other* pool path gets a plausible decoy, plus a standard Linux home skeleton and the demo DB `Documents/inventory.db`, so the real file isn't identifiable by name. `.bash_history` is always rewritten with a hint naming the hidden file's *directory* (not the file), seeded deterministically from student and path. Otherwise generation is idempotent: existing DB rows are skipped and existing files on disk are never overwritten; `--force` regenerates and rewrites the old hidden file back to a decoy. `--variant path` is the harder variant: the hidden file holds the Caesar-encrypted *path* to a second pool file containing the plaintext password (`variant`/`password_file_path` columns, added to old DBs via `ensure_columns()`); it uses two unique pool paths per student. Login still only compares `plain_password`, so the server is variant-agnostic. Never remove the original 24 paths from `HIDDEN_DIRS`, because existing students' real files live there. Each directory should keep several files so the history hint doesn't give away the file.

**Task №4 (`ctf/configs/`, `server/config_task.py`).** `generate_configs.py` builds a Debian 12 server tree per student (SSH, Apache, MariaDB, PHP configs from `templates.py`, with traps: client `ssh_config`, `sshd_config.d` drop-in, `sites-available`/`sites-enabled` symlinks, `cli/php.ini`, templates and backups) and stores personal targets + SHA-256 of decoy files in `ib_config_tasks.params` (JSON). `config_task.check()` evaluates the *effective* values the way each service reads them (sshd: first value incl. `Include`; Apache: last value, `Listen` outside `<IfModule>`, the enabled site; MariaDB: last `bind-address` in server sections; PHP: the apache2 php.ini) and returns stages in the `run_all.py` report shape; the decoy stage is `required: False`. The terminal re-checks after every command that wrote files (`ctx.wrote`) and saves progress (`save_progress`, solved is sticky); the `check` command prints the stages. Student statement: `ctf/configs/TASK.md` (cut at `## Для преподавателя`, placeholders `{ssh_port}` etc.); theory shown in mdtask: `ctf/configs/THEORY.md`; instructor guide: `task/№4.Config-files-find-sed.md`.

**Task №5 (`ctf/terminal/`, `server/terminal_task.py`).** A step-by-step trainer: 14 stages in `STAGES` (title, intro lines, items). Each item is one of three kinds: `fs` (checks the sandbox state via `Env`), `cmd` (checks `ib_terminal_log` entries logged *after the stage opened*, i.e. with `id > progress.opened[k]`), or `answer` (a question answered with `answer <qid> <value>`; it is accepted only on the current stage). `advance()` completes stages strictly in order, and a completed stage stays completed (later stages change files). Progress JSON lives in `ib_terminal_tasks.progress` (`done`, `opened`, `completed_at`, `answers`, `attempts`). Every shell line is logged to `ib_terminal_log` (raw and expanded line, `ctx.trace`, status) by `terminal_record()` in `app.py`, which then runs `advance()` and prints stage messages. The terminal has `task [N]` (stage text with ✔/✘), `check` and `answer` hooks. `generate_terminal.py` builds the sandbox, stores derived values in `params` (log line counts, ERROR lines, top IP, SHA-256 of files to copy) and writes `~/TASK.md` from `STAGES` (`task_markdown()`), so stage text lives only in Python. The mdtask copy of stage titles is checked by a test. Theory shown in mdtask: `ctf/terminal/THEORY.md`; instructor guide: `task/№5.Terminal-basics.md`.

**Tasks №6–7 (`server/lab_task.py` engine).** Same stage model as №5, but generic: a `Lab` object (key, number, title, `STAGES`, intro, sandbox dir) registered by `server/incident_task.py` (№6 `incident`, from scenario «Миссия 5») and `server/ssh_task.py` (№7 `ssh`, «Миссия 3»); source scenarios are in `<mdtask>/data/TermialEmulatorScenariy/`. Progress and the command log live in the shared tables `ib_lab_tasks` / `ib_lab_log` (column `task`), sandboxes in `data/ctf/<sandbox_dir>/<id>/` (`CTF_LABS_DIR`). Stages have a `goal` and `intro` (step-by-step how-to, shown by `task`, in `~/TASK.md` and after login: `/api/login` returns `welcome`, which `terminal-lab.html` prints). Items may be `critical: True` (must hold all the time: log intact, admin keeps access): `broken_critical()` checks those of opened stages after every command that wrote (`ctx.wrote`) and prints a warning. `app.py` wires them via `LabState`, `lab_hooks`, `lab_record`, `lab_welcome`. Generators share `ctf/lab_gen.py` (Debian skeleton, CLI, `ib_lab_tasks` rows); №6 `ctf/incident/generate_incident.py` builds a personal `auth.log`/`wtmp`/`btmp` incident and stores the expected answers, timeline lines and log SHA-256 in `params`; №7 `ctf/ssh/generate_ssh.py` builds an insecure OpenSSH setup. Admin commands are in `server/cmd_admin.py` (`passwd`, `usermod`, `gpasswd`, `deluser`, `getent`, `groups`, `id USER`, `last`, `lastb`, `sha256sum`, `md5sum`, `systemctl`, `journalctl`, `sshd -t/-T`, `ssh`, `ssh-keygen`), accounts parsing in `server/accounts.py`, the SSH model in `server/sshd_sim.py` (Include + first-value semantics, sshd -t errors, service state in `/var/lib/seclab/sshd.json` applied only on reload/restart, `login()` decision incl. Allow/Deny, PermitRootLogin, StrictModes, authorized_keys; `ssh` records `{user, ok, method}` into its trace entry for `cmd` checks and appends to `auth.log`). Keys are fake: `derive_pub()` hashes the private body. Theory: `ctf/incident/THEORY.md`, `ctf/ssh/THEORY.md`; instructor guides: `task/№6.Incident-response.md`, `task/№7.SSH-secure-access.md`; tests: `tests/test_labs.py`.

**Task №8 (`server/logs_task.py`, `ctf/logs/generate_logs.py`, plan `<mdtask>/docs/ib-task8-logs-plan.md`).** Log investigation on one of three themes (shop/library/clinic): auth.log in UTC with the brute force split across rotation, nginx access logs with `+0500`, a proxy and `X-Forwarded-For` (the real client is the last address), injected fake lines without `rt=`/`cid=` (one is an «instruction for the AI analyzer» naming a framed address), an app log with a `seq=`/`prev=` hash chain (two groups of lines deleted, one line's time changed) and an untouched `audit.csv`. Generic engine extras in `lab_task.py`, all opt-in per `Lab`: `track_output` stores tokens seen in command output (`ib_lab_seen`; values typed in the command line and output of `echo`/`printf`/`answer`… don't count) and items with `proof` accept an answer only if it (or the values it is derived from) was seen; `trap` rejects AI-bait answers into `progress.traps`; 3 wrong answers in a row → 2-minute pause; `defense` asks 2 timed multiple-choice questions after a stage's items are done (`answer q N`, 60 s, wrong/late halves the stage in `score`); `before_run` (the live «Дежурство SOC» journal: `shift_plan()` derives a 25-minute shift from the seed and shift number, lines are appended on each command, blocked addresses stop appearing), `commands` (`duty`, `timeline`), `load_ext` (the detector row from mdtask's `ib_logs_detector`); `lab_task.NOW` is patched in tests. New shell commands in `server/cmd_logs.py`: `zcat`, `zgrep`, `tr`, `date -d` with `TZ=` (the shell now honours `VAR=value cmd` prefixes), an `iptables` subset stored in `/etc/iptables/rules.v4`, `journalctl --verify --file`. Tests: `tests/test_logs_task.py` (data per seed, a 100-point walkthrough, proof, traps, duty).

**Task №9 (`server/grep_task.py`, `ctf/grep/generate_grep.py`, plan `<mdtask>/docs/ib-task9-grep-plan.md`).** 13 grep tasks, one stage each. The answer is the command itself: `Lab.on_command` (called by `lab_record` before `advance`) takes every line whose pipeline contains grep, refuses anything but grep/egrep/fgrep (no redirections, `$(...)`, `; && ||`), runs it with `run_in()` (a read-only `Sandbox` on any root, cwd created if missing) and compares the normalized output with the reference from `<mdtask>/scripts/ib/solutions/grep.json` (placeholders `<emp>`, `<svc>`, `<domain_re>`) on the student's sandbox, refuses a result typed in the command, then reruns both on the hidden sets `data/ctf/grep-check/<id>/1|2` (written by the generator with the same paths and personal values, other content; edge cases in every set). Solved → `progress.answers["gK"]`, `progress.grep[K]` (tries, opened/solved time, accepted command, `mut`: a mutation of the command — flag/anchor/escape removed — with its real line count, asked as the first control question). `grep.json` also lists «almost right» commands per task; `tests/test_grep_task.py` checks on 12 seeds that each of them differs from the reference on at least one set. `hint` prints the theory section and is counted in `progress.hints`. Score 3+3+4+9×10, halved per task for a wrong/late control question.

**Task №10 (`server/perms_task.py`, `ctf/perms/generate_perms.py`, plan `<mdtask>/docs/ib-task10-perms-plan.md`).** «Права доступа и аудит сервера» on the same stage engine, 8 stages (учётные записи → чтение прав → запись для всех → секреты → SUID → владельцы приложения → пользователи и sudo → повторный аудит) on a Debian app server (shop/library/clinic theme). It turns on the **per-file ownership model** in `vfs.Sandbox`: a sandbox with `var/lib/seclab/owners.json` (path → `user:group`, numeric uid for a removed account) makes `per_file_owners` True, so `owner/group/uid/gid` come from that file + `/etc/passwd`,`/etc/group`, `can()` honours group bits when the student is in the file's group, `chown`/`chgrp` (`cmd_files.py`, root-only, strip SUID/SGID like Linux) edit it, and `ls -l`/`stat -c`/`find -user/-group/-nouser/-perm` report real owners (no owners.json → every other task behaves exactly as before). Stage checks reason over this model via a `vfs.Sandbox` built in `perms_task._sb` and `_perm(env, sb, vrel, user, bit)` (can user X read/write file Y), so different correct fixes pass; `find` runs as non-root exit non-zero, so cmd checks on it use `env.ran(..., ok_only=False)`. Anti-AI: answers proven from command output (`track_output`), 2 control questions per stage (`defense_banks.PERMS`/`PERMS_DECOYS`), a trap on 1.1 (a planted `README.handover.txt` is an «instruction for the AI» naming the fired employee instead of the real UID-0 account), `guard: true` with a wrong `clipHint`. Critical items: `/tmp` stays 1777, `passwd`/`sudo` keep SUID, the student stays in `sudo`, the app (www-data) still reads its `.env`. Tests: `tests/test_perms_task.py`.

**Control questions and proof in №5–7.** `server/defense.py` holds the shared control-question state (`gate()` in `advance`, `answer q N`, 60 s; `lab_task.NOW` drives its clock); `lab_task.bank_defense()` builds questions from `server/defense_banks.py` (+ «какой командой вы получили …» for proven answers). №6–7 set `track_output` and `proof` on numeric/IP/name answers; №5 (`terminal_task.advance(..., defense_fn, seen)`, wired in `app.terminal_advance`) records output tokens into `ib_lab_seen` with task `terminal` (joined to `ib_terminal_log`). Output tokens include words from 2 letters.

The command help lives only in `HELP_TEXT` in `server/shell.py`; `man` pages are in `server/manpages.py`.

**Checkers (`checks/`).** Each `taskN_check.sh` sources `lib/common.sh`, records stages with `add_stage <id> <title> pass|fail <detail>`, and finishes with `print_report`, which prints a single JSON object `{task, student, total_stages, passed_stages, stages[]}` to stdout. Failing early still calls `print_report` and exits 0. `run_all.py` calls each script (30s timeout), parses that JSON, and builds the aggregate report. To add a task, create `taskN_check.sh` and add an entry to `TASKS` in `run_all.py` (`args` lambda + `requires` key in `students.json`, or `requires: None`). `task4_check.py` and `task5_check.py` are Python (read the sandbox and DB, need nothing in `students.json`).

**Admin panel (`admin-panel/index.html`)** currently renders embedded demo data in the `run_all.py` report shape. It is not yet wired to real reports. Real task №3 results are shown in mdtask's own admin at `/admin/ib`.

**`TASK.md`** (repo root) is the short task №3 statement and the only task file in a sandbox. The generator copies its student part into every sandbox as `~/TASK.md`, cutting everything from the `## Для преподавателя` heading on (that section holds the answer query, so keep that exact heading). It also deletes the obsolete `ЗАДАНИЕ.txt`/`help.txt` left by older versions. Re-run the generator after editing it.

**Tasks (`task/№<n>.<Name>.md`)** are step-by-step instructor/infra guides. `docs/practical-modules-plan.md` is the overall course plan.

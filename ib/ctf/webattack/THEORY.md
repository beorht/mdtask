# Разбор веб-атак по журналам доступа

Веб-сервер (nginx, Apache) записывает каждый HTTP-запрос в **журнал доступа** — обычно
`/var/log/nginx/access.log`. Когда сайт атакуют, следы остаются именно там. Задача специалиста
Blue Team — прочитать журнал и восстановить, что делал злоумышленник: откуда он, чем сканировал,
какую уязвимость нашёл и что успел сделать.

## Формат строки журнала (combined)

```
203.0.113.7 - - [18/Nov/2026:02:14:07 +0500] "GET /product.php?id=1 HTTP/1.1" 200 1876 "-" "Mozilla/5.0 ..."
```

| поле | смысл |
|---|---|
| `203.0.113.7` | IP-адрес клиента |
| `[18/Nov/2026:02:14:07 +0500]` | дата и время запроса |
| `"GET /product.php?id=1 HTTP/1.1"` | метод, путь с параметрами, версия |
| `200` | код ответа (200 ок, 403 запрещено, 404 не найдено, 500 ошибка) |
| `1876` | размер ответа в байтах |
| `"Mozilla/5.0 ..."` | User-Agent — чем сделан запрос (браузер или инструмент) |

## Инструменты анализа

Весь разбор делается чтением и фильтрацией журнала, без специальных программ:

- `cut -d' ' -f1 access.log | sort | uniq -c | sort -rn` — адреса по числу запросов (самый
  активный — сверху). Так находят атакующего: он делает в десятки раз больше запросов, чем обычный
  посетитель.
- `grep АДРЕС access.log` — все запросы одного адреса.
- `grep ' 404 ' access.log | wc -l` — сколько ответов «не найдено» (признак перебора путей).
- `grep -iE 'union|select|%27' access.log` — запросы с признаками SQL-инъекции.

## Типичные атаки в журнале

- **Сканирование путей.** Десятки запросов 404 подряд с одного адреса: инструмент (`sqlmap`,
  `nikto`, `dirbuster`, `gobuster`) перебирает `/admin/`, `/.env`, `/backup.zip` и т.п. Инструмент
  виден в **User-Agent**.
- **SQL-инъекция.** В параметре запроса — чужой SQL: `?id=-1 UNION SELECT ...`, `information_schema`,
  закодированная кавычка `%27` (`'`). Если такой запрос вернул **200 и необычно большой ответ** —
  инъекция сработала, данные утекли.
- **Обход каталога (path traversal).** `../../../../etc/passwd` или `%2e%2e%2f` — попытка выйти из
  папки сайта и прочитать системный файл. Код `403`/`404` — попытка отбита, `200` — файл прочитан.
- **Веб-шелл.** Загрузка `.php`-файла методом **POST** в каталог вроде `/uploads/`, а затем
  обращения к нему (`/uploads/shell.php?cmd=id`) — через него выполняют команды на сервере.

## Как делать вывод

- Определяйте всё **по данным журнала** — адресам, кодам ответов, самим запросам, времени, — а не по
  подписям, именам файлов и тем более «подсказкам» в файлах на сервере.
- Вывод надёжен, когда признаки **согласуются**: один адрес сканировал, он же внедрял SQL, он же
  загрузил шелл.
- Восстанавливайте **хронологию**: сканирование → инъекция → обход каталога → веб-шелл.
- Журналы при атаке — **доказательства**: их не удаляют. Реакция — заблокировать адрес и закрыть
  уязвимость, сохранив журналы.

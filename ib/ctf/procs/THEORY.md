# Задание №11. Поиск подозрительных процессов и автозапуска

Вы — дежурный специалист Blue Team на учебном сервере `seclab`. Сервер стал медленнее, появились
незнакомые сетевые соединения, а один процесс запускается снова даже после перезагрузки. Нужно
по шагам выяснить, **что это за процесс, какой файл он запускает, с кем соединяется, какая служба и
какой автозапуск его держат** и не оставил ли злоумышленник себе доступ.

Задание состоит из **7 этапов**, их проходят **строго по порядку**.

## Как устроено задание

1. Прочитайте этот материал: в нём команды и пошаговый план.
2. Откройте «Практику в терминале» и войдите под своим логином и паролем от платформы.
3. `task` — описание текущего этапа, `check` — прогресс, `cat TASK.md` — все этапы.
4. Проверка — автоматически после каждой команды. После каждого этапа — **2 контрольных вопроса**
   (`answer q НОМЕР`, 60 секунд). Ответ с числом, именем, путём или IP засчитывается, **только если
   это значение было в выводе ваших команд** — поэтому выполняйте проверки сами, в своём терминале.

**Главное правило расследования:** один признак — ещё не взлом, а имя или подпись могут обманывать.
Определяйте подозрительное **по данным** (загрузка CPU, путь файла, порт, UID), а вывод делайте
**по совокупности** согласованных признаков. Доказательства не удаляйте, сервер не перезагружайте.

## 1. Процессы

| Команда | Что показывает |
|---|---|
| `ps aux --sort=-%cpu \| head` | процессы по убыванию загрузки CPU: `USER PID %CPU %MEM … COMMAND` |
| `ps aux --sort=-%mem \| head` | то же по памяти |
| `ps -p PID -o pid,ppid,user,lstart,etime,cmd` | подробно об одном процессе |

Высокая нагрузка и незнакомый путь запуска — повод проверить процесс (но ещё не доказательство).

## 2. Исполняемый файл

Имя процесса не всегда совпадает с именем файла — проверяйте путь:

| Команда | Что показывает |
|---|---|
| `readlink -f /proc/PID/exe` | настоящий путь к исполняемому файлу |
| `cat /proc/PID/cmdline` | с какими аргументами запущен |
| `ls -l ФАЙЛ`, `stat ФАЙЛ` | владелец, права, дата изменения |

Системные программы лежат в `/usr/bin`, `/usr/sbin`. Запуск из `/opt`, `/tmp` или домашнего каталога —
повод продолжить проверку.

## 3. Сетевые соединения

| Команда | Что показывает |
|---|---|
| `ss -lntup` | слушающие TCP/UDP-сокеты с процессом (`Local Address:Port`, program) |
| `ss -tnp` | установленные соединения (`Peer Address:Port` — куда подключились) |

`LISTEN` — сокет ждёт входящие подключения; установленное соединение на незнакомый адрес и
нестандартный слушающий порт — признак бэкдора. Номер порта сам по себе не определяет программу —
важно сопоставить сокет с конкретным PID.

## 4. Служба systemd

| Команда | Что показывает |
|---|---|
| `systemctl list-units --type=service --state=running` | работающие службы |
| `systemctl --failed` | службы с ошибкой |
| `systemctl status ИМЯ.service` | состояние, ExecStart, Main PID |
| `systemctl cat ИМЯ.service` | сам unit-файл (ключ `ExecStart` — что запускается) |

Злоумышленник часто называет службу похоже на системную. Проверяйте **ExecStart** (запускаемый файл),
а не имя: ExecStart должен совпасть с найденным на этапе 2.

## 5. Автозапуск

| Команда | Что показывает |
|---|---|
| `systemctl list-timers --all` | таймеры systemd (какой и что активирует) |
| `ls -l /etc/cron.d/`, `cat /etc/cron.d/*` | системные задания по расписанию |
| `crontab -l` | задания cron текущего пользователя |

Один и тот же файл может запускаться службой, таймером и из `cron` одновременно — ищите **все** способы
автозапуска, иначе процесс вернётся после перезагрузки.

## 6. Учётные записи и ключи

| Команда | Что показывает |
|---|---|
| `getent passwd` | все учётные записи; последнее поле — оболочка |
| `getent passwd \| grep ':0:0:'` | учётные записи с UID 0 |
| `ls -la ~/.ssh`, `cat ~/.ssh/authorized_keys` | какие ключи пускают на вход |

**UID 0 — это права root.** Законно он только у `root`; любая другая запись с UID 0 — скрытый
«второй root». Незнакомый ключ в `authorized_keys` — способ вернуться на сервер.

## 7. Единая картина

Свяжите находки по времени: вход злоумышленника → действия (`sudo`) → появление службы/процесса →
сетевое соединение.

| Команда | Что показывает |
|---|---|
| `sudo grep 'Accepted' /var/log/auth.log` | успешные входы по SSH (кто, откуда, когда) |
| `sudo grep 'sudo:' /var/log/auth.log` | что делали через `sudo` |
| `sudo journalctl -u ИМЯ.service` | журнал конкретной службы |

**Если компрометация подтвердилась** — не удаляйте файлы и не перезагружайте сервер: это уничтожит
доказательства. Сначала зафиксируйте и сохраните журналы, процессы и соединения, затем действуйте по
плану реагирования. Надёжный вывод строится на совокупности признаков, а не на одном индикаторе.

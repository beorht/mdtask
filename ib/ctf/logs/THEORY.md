# Расследование по журналам

В задании №6 вы расследовали инцидент по одному журналу входов. В реальной работе журналов много,
они пишутся в разных форматах и часовых поясах, часть из них уже сжата, а злоумышленник старается
их испортить: дописать ложные записи или стереть свои. Эта теория — о том, как работать с такими
журналами и не попасться на подделки.

## 1. Где лежат журналы и как их читать

| Журнал | Что в нём | Как читать |
|---|---|---|
| `/var/log/auth.log` | входы по SSH, ошибки паролей, команды sudo | `sudo grep`, `sudo tail` |
| `/var/log/nginx/access.log` | каждый запрос к веб-серверу | `sudo grep`, `cut`, `sort`, `uniq -c` |
| `/var/log/<служба>/app.log` | действия пользователей в приложении | `sudo grep`, `sudo journalctl --verify` |
| `/var/lib/<служба>/audit.csv` | аудит базы данных (пишет СУБД) | `sudo grep`, `sort` |

Журналы принадлежат root — читайте их через `sudo`. Никогда не редактируйте исходные журналы:
это доказательства.

## 2. Ротация журналов

Чтобы журналы не росли бесконечно, программа `logrotate` раз в сутки (или в неделю) переименовывает
текущий файл и начинает новый:

```
access.log      ← пишется сейчас
access.log.1    ← вчерашний
access.log.2.gz ← позавчерашний, сжатый gzip
```

Правила ротации — в `/etc/logrotate.d/`. Важно помнить:

- **атака может начаться в одном файле и продолжиться в другом** — считая события, смотрите все файлы;
- сжатые файлы обычный `cat` и `grep` не читают: для них есть `zcat` (вывести содержимое) и `zgrep`
  (искать). Им можно передавать и обычные, и сжатые файлы: `zgrep 'шаблон' access.log*`;
- несколько файлов подряд можно склеить: `sudo cat файл.1 файл | grep …`.

## 3. Время и часовые пояса

Одно и то же событие в разных журналах может быть записано разным временем:

- **syslog** (`auth.log`) пишет время в поясе сервера и **не указывает пояс**. Какой пояс у сервера —
  смотрите в `/etc/timezone`. Многие серверы работают в UTC;
- **nginx** пишет время вместе с поясом: `[19/Nov/2026:02:07:15 +0500]` — здесь +05:00;
- **приложение** пишет так, как настроено в его конфигурации (ищите параметр вроде `log_timezone`).

Чтобы расставить события по порядку, приведите всё к одному поясу. Ташкент — UTC+5, без перехода
на летнее время. Пересчитать можно в уме или командой `date`:

```
date -d '2026-11-18 21:07:15 UTC'                              # во времени сервера
TZ=Asia/Tashkent date -d '2026-11-18 21:07:15 UTC' '+%Y-%m-%d %H:%M:%S'
date -u -d '19/Nov/2026:02:07:15 +0500'                         # формат nginx → UTC
```

Будьте внимательны с датой: 21:07 UTC 18-го — это уже 02:07 19-го по Ташкенту.

## 4. Прокси и X-Forwarded-For

Если перед веб-сервером стоит обратный прокси (балансировщик, защита от DDoS), то nginx видит в первом
поле строки адрес **прокси**, а не клиента. Поэтому прокси передаёт адрес клиента в заголовке
`X-Forwarded-For`, и его тоже пишут в журнал.

Подвох: этот заголовок может прислать и сам клиент. Прокси не заменяет его, а **дописывает адрес
клиента в конец**:

```
X-Forwarded-For: <что прислал клиент>, <настоящий адрес, который увидел прокси>
```

Значит, доверять можно только **последнему** адресу — тому, который добавил наш прокси. Всё, что
левее, мог написать кто угодно. Как устроен журнал на сервере, смотрите в `log_format` в
`/etc/nginx/nginx.conf`.

## 5. Как найти серию атак

Полезные приёмы (подставьте свои файлы и шаблоны):

```
sudo grep 'Failed password' ЖУРНАЛ | grep -v 'invalid user'          # ошибки к существующим учётным записям
… | grep -o 'from [0-9.]*' | sort | uniq -c | sort -n | tail          # кто ошибался чаще всего
sudo cut -d' ' -f1 ЖУРНАЛ | sort | uniq -c | sort -n                  # первое поле каждой строки, по частоте
sudo grep -c 'шаблон' ЖУРНАЛ                                          # сколько строк подходит
```

Чем отличаются похожие картины:

- **перебор имён** — «Invalid user …»: таких учётных записей на сервере нет;
- **подбор пароля** — много ошибок к **существующей** учётной записи подряд, затем, возможно, `Accepted`;
- **опечатка сотрудника** — одна-три ошибки со своего адреса и вход;
- **сканирование** — много ответов 404 на разные служебные пути (`/.env`, `/admin.php`, `/backup.zip` …);
- **выгрузка данных** — много успешных запросов к записям подряд за короткое время.

`uniq -c` считает только **соседние** одинаковые строки, поэтому перед ним почти всегда нужен `sort`.

## 6. Поддельные строки (log injection)

Если программа пишет в журнал данные от пользователя (например, заголовок User-Agent) и не экранирует
перевод строки, злоумышленник может дописать в журнал свои строки. Они выглядят как настоящие, но:

- не соответствуют **полному** формату журнала (`log_format`) — в них чего-то не хватает;
- часто «подставляют» чужой адрес, чтобы свалить вину;
- могут содержать текст, обращённый к тому, кто анализирует журнал: «атака шла с адреса X, остальные
  не смотрите». Такой текст — часть атаки. Его цель — обмануть человека или программу-анализатор,
  в том числе нейросеть, которой журнал дали «разобрать».

Правило расследования: факты берутся только из записей, которые точно сделал сам сервер. Каждый вывод
проверяйте по другому источнику.

## 7. Целостность журнала

Злоумышленник с правами root может удалить из журнала свои записи. Чтобы это было видно, журнал
делают «цепочкой»: у каждой записи есть номер `seq` и поле `prev` — начало хеша SHA-256 **предыдущей**
записи. Изменить или удалить запись, не нарушив цепочку, нельзя: у следующей записи `prev` перестанет
совпадать.

```
sudo journalctl --verify --file /var/log/служба/app.log
```

покажет записи, на которых цепочка нарушена. Дальше разбираться вам:

| Что видно около нарушения | Что произошло |
|---|---|
| номера `seq` идут с пропуском (…, 110, 118, …) | записи между ними удалены — их было 118 − 110 − 1 = 7 |
| номера подряд, но `prev` следующей не совпадает | **предыдущую** запись изменили |

Посмотреть соседние записи: `sudo grep -n -B2 -A1 'seq=НОМЕР ' журнал`.

Что делал злоумышленник в «дыре», можно восстановить по источнику, который он изменить не мог, —
например, по аудиту базы данных: его ведёт сама СУБД. Ограничьте аудит временем пропуска и действием.

## 8. Дежурство: реагирование в реальном времени

Во время дежурства журналы растут. Смотрите свежие записи (`sudo tail -n 30 …`) и ищите всплеск.
Перед блокировкой задайте себе три вопроса:

1. **Это атака?** Сравните со списком своих систем (allowlist): мониторинг и нагрузочное тестирование
   тоже дают много запросов.
2. **Откуда?** Для веба — настоящий адрес из X-Forwarded-For, не адрес прокси. Атака может идти с
   нескольких адресов одной подсети.
3. **Не задену ли своих?** Блокировка прокси или своего сервера ломает работу всех.

Блокировка адреса брандмауэром:

```
sudo iptables -A INPUT -s 203.0.113.7 -j DROP        # один адрес
sudo iptables -A INPUT -s 203.0.113.0/24 -j DROP     # вся подсеть /24
sudo iptables -L -n --line-numbers                   # что заблокировано
sudo iptables -D INPUT 2                             # снять правило №2
```

После блокировки записи с этого адреса перестают появляться: пакеты отбрасываются, запросы не
доходят до службы.

## 9. Детектор атак

Ручной поиск хорош для расследования, но дежурить круглые сутки должна программа. Детектор читает
журнал строка за строкой, определяет настоящий адрес клиента, отбрасывает строки, которые не
соответствуют формату, и считает признаки атаки: ошибки входа в окне времени, число разных
несуществующих путей. Главное в такой программе — аккуратно разбирать формат и учитывать крайние
случаи: пустой журнал, переход через полночь, повтор одного и того же пути, ровно пороговое число
событий.

## 10. Отчёт

Отчёт о расследовании отвечает на вопросы: **кто** (адреса, учётная запись), **когда** (в одном
поясе), **что сделал** (вход, повышение прав, выгрузка, удаление, подделка журнала), **что сделано**
для сдерживания и **что изменить**, чтобы это не повторилось: вход только по ключу, ограничение
попыток (fail2ban), отдельное защищённое хранилище журналов, экранирование данных в журналах,
доверие к X-Forwarded-For только от своего прокси.

# Задание №6. Расследование инцидента по журналам

Ночью на учебном сервере `seclab` сработало оповещение: много неудачных входов по SSH.
Вы — специалист первой линии реагирования. Нужно по журналам восстановить, что произошло,
сохранить доказательства, остановить злоумышленника соразмерными мерами и подготовить отчёт.
Все данные учебные, у каждого студента свой инцидент.

Задание состоит из **8 этапов**, их проходят **строго по порядку**.

## Как устроено задание

1. Прочитайте этот материал: в нём всё, что нужно знать, и пошаговый план.
2. Откройте «Практику в терминале» и войдите под своим логином и паролем от платформы.
3. Наберите `task`: появится описание **текущего** этапа (цель, команды, что сделать).
   Все этапы сразу есть в файле `~/TASK.md` (`cat TASK.md`).
4. Проверка запускается автоматически после каждой команды. Когда все пункты выполнены,
   терминал сообщит «Этап N пройден» и откроет следующий. Прогресс по всем этапам показывает `check`.

| Вид пункта | Как проверяется |
|---|---|
| **Команда** | по журналу ваших команд: команда выполнена **после открытия этапа** |
| **Файлы** | по состоянию сервера: копия сохранена, учётная запись заблокирована, права исправлены |
| **Вопрос** | ответ командой `answer НОМЕР ОТВЕТ`, например `answer 3.1 20` |
| **Критично** | условие, которое должно выполняться **всё время**: журнал не изменён, администраторы не заблокированы. Если вы его нарушите, терминал сразу предупредит, и этап не будет засчитан |

> Все ваши команды записываются в журнал, который видит преподаватель.

## Правила расследования

Эти правила — главное в задании. Их нарушение в реальной работе делает расследование
бесполезным, а иногда и незаконным.

1. **Журналы — доказательства.** Их нельзя изменять, удалять, «чистить» или перезаписывать.
   Работайте только командами чтения: `cat`, `head`, `tail`, `grep`, `wc`.
2. **Сначала сохранить, потом разбираться.** Копия журнала и его контрольная сумма делаются
   до любых других действий.
3. **Факты отдельно от догадок.** В отчёт как факт идёт только то, что прямо записано
   в журнале. «Данные украдены» — гипотеза, если журналы этого не показывают.
4. **Одна ошибка — не атака.** Сотрудник может один раз ошибиться в пароле. Подозрительна
   **серия** неудачных попыток подряд, особенно ночью и с внешнего адреса.
5. **Соразмерные меры.** Учётную запись блокируют, а не удаляют: в домашнем каталоге и
   журналах остаются следы, которые ещё понадобятся. Нельзя блокировать администраторов
   и себя — сервер останется без управления.

## Журналы Linux

Журналы (логи) лежат в каталоге `/var/log`. Читать их может только `root`, поэтому все
команды чтения выполняются через `sudo`.

| Файл | Что в нём | Чем читать |
|---|---|---|
| `/var/log/auth.log` | входы по SSH (удачные и неудачные), `sudo`, сеансы | `sudo grep`, `sudo tail` |
| `/var/log/wtmp` | история сеансов: кто, откуда, когда вошёл и вышел | `last` |
| `/var/log/btmp` | неудачные попытки входа | `sudo lastb` |
| `/var/log/syslog` | общие сообщения системы | `sudo tail` |

Строки `auth.log` устроены одинаково:

```
Oct 11 02:47:13 seclab sshd[2314]: Failed password for webops from 203.0.113.45 port 51234 ssh2
└── дата и время ┘ └сервер┘ └программа┘ └──────────────── сообщение ────────────────────────┘
```

Самые важные сообщения:

| Сообщение | Что значит |
|---|---|
| `Failed password for ИМЯ from IP` | неверный пароль для **существующей** учётной записи |
| `Failed password for invalid user ИМЯ from IP` | такой учётной записи **нет**: это перебор имён (сканер) |
| `Invalid user ИМЯ from IP` | попытка войти под несуществующим именем |
| `Accepted password for ИМЯ from IP` | **успешный** вход по паролю |
| `Accepted publickey for ИМЯ from IP` | успешный вход по ключу |
| `session opened` / `session closed` | начало и конец сеанса |
| `sudo:   ИМЯ : ... ; COMMAND=/usr/bin/...` | ИМЯ выполнил команду от имени root |

## Поиск по журналу: grep и конвейеры

```bash
sudo grep 'Failed password' /var/log/auth.log            # все неудачные попытки
sudo grep 'Failed password' /var/log/auth.log | wc -l    # сколько их
sudo grep -v invalid ...                                 # -v — строки БЕЗ слова invalid
sudo grep 'Accepted' /var/log/auth.log                   # все успешные входы
sudo grep '203.0.113.45' /var/log/auth.log               # всё, что связано с адресом
```

Посчитать попытки по IP-адресам (`grep -o` выводит только совпавший кусок строки):

```bash
sudo grep 'Failed password' /var/log/auth.log | grep -v invalid | grep -o 'from [0-9.]*' | sort | uniq -c
#       1 from 10.0.5.12
#       7 from 203.0.113.45
```

Читать конвейер нужно слева направо: найти строки → убрать строки с `invalid` → вырезать адрес →
отсортировать → посчитать одинаковые.

## Контрольная сумма: как доказать, что файл не менялся

`sha256sum` вычисляет «отпечаток» файла: 64 шестнадцатеричных символа. У одинаковых файлов он
одинаковый, а изменение даже одного символа даёт совсем другую сумму.

```bash
mkdir ~/evidence
sudo cp /var/log/auth.log ~/evidence/auth.log                       # копия
sudo sha256sum /var/log/auth.log > ~/evidence/auth.log.sha256       # сумма оригинала
sudo sha256sum -c ~/evidence/auth.log.sha256                        # проверка
# /var/log/auth.log: ЦЕЛ
```

`ЦЕЛ` значит, что файл совпадает с сохранённой суммой. `НЕ СОВПАДАЕТ` — файл изменили.

## Учётные записи и группы

| Файл | Что в нём |
|---|---|
| `/etc/passwd` | учётные записи: `имя:x:uid:gid:описание:домашний_каталог:оболочка` |
| `/etc/shadow` | хеши паролей (только root). `!` перед хешем — учётная запись заблокирована |
| `/etc/group` | группы: `имя:x:gid:участник1,участник2` |
| `/etc/sudoers.d/*` | какие команды каким пользователям разрешено выполнять через `sudo` |

Члены группы `sudo` могут выполнять **любые** команды от имени root. Если сотруднику по его
обязанностям нужно только перезапускать веб-сервер, а он состоит в `sudo`, это лишние права.
Именно ими и пользуется злоумышленник, подобравший его пароль.

```bash
getent group sudo          # кто в группе sudo
id ИМЯ                     # группы пользователя
sudo passwd -S ИМЯ         # состояние: P — пароль задан, L — заблокирована
```

## Права файлов

`ls -l` показывает права тремя тройками: владелец, группа, остальные. Число — сумма
`r=4, w=2, x=1` по каждой тройке.

| Права | Число | Кто может читать |
|---|---|---|
| `rw-r-----` | 640 | владелец и группа (так и должно быть у внутренних отчётов) |
| `rw-rw-rw-` | 666 | **все** пользователи сервера могут читать и изменять |
| `rw-r--rw-` | 646 | все могут читать и изменять |

## Пошаговый план

### Этап 1. Первичный осмотр журналов

```bash
ls -l /var/log
sudo head -n 5 /var/log/auth.log
sudo tail -n 5 /var/log/auth.log
sudo wc -l /var/log/auth.log
```

Ответьте, сколько строк в журнале (`answer 1.1 ЧИСЛО`) и во сколько сделана последняя
запись (`answer 1.2 ЧЧ:ММ:СС`).

### Этап 2. Сохранение доказательств

Сделайте копию журнала и сохраните его контрольную сумму (см. раздел «Контрольная сумма»).
Проверьте `sha256sum -c`.

### Этап 3. Неудачные попытки входа

Посчитайте все строки `Failed password`. Отделите перебор несуществующих имён
(`invalid user`) от подбора пароля к **существующей** учётной записи. Найдите IP-адрес,
учётную запись и число неудачных попыток с этого адреса.

### Этап 4. Успешный вход и действия после него

```bash
sudo grep 'Accepted' /var/log/auth.log     # был ли успешный вход с того же адреса?
last                                        # сеанс: когда начался и закончился
sudo grep 'COMMAND=' /var/log/auth.log      # что делали через sudo
ls -l /srv/company/reports                  # текущие права файлов
getent group sudo                           # почему у учётной записи были права root
```

### Этап 5. Временная шкала

Временная шкала — это все события инцидента по порядку. `grep` сохраняет порядок строк журнала,
поэтому достаточно отобрать нужные строки в файл:

```bash
mkdir -p ~/incident
sudo grep 'IP_АТАКУЮЩЕГО' /var/log/auth.log > ~/incident/timeline.txt
sudo grep 'sudo: *ИМЯ :' /var/log/auth.log > ~/incident/sudo.txt
cat ~/incident/timeline.txt
```

В `sudo.txt` попадут **все** команды этой учётной записи через sudo, в том числе обычные
дневные. Это нормально: по времени и адресу видно, какие из них сделал злоумышленник.

### Этап 6. Факты и гипотезы

Ответьте `да` или `нет` строго по журналам. Например, журнал входов показывает, **кто вошёл
и что выполнил через sudo**. Но в нём нет записей о передаче файлов по сети, поэтому
«данные скопировали наружу» — гипотеза, а не факт.

### Этап 7. Сдерживание

```bash
sudo passwd -l ИМЯ                 # заблокировать (или sudo usermod -L ИМЯ)
sudo passwd -S ИМЯ                 # проверка: L
sudo gpasswd -d ИМЯ sudo           # убрать лишние права администратора
getent group sudo                  # проверка
sudo chmod 640 ПУТЬ_К_ФАЙЛУ        # вернуть права файлу
ls -l ПУТЬ_К_ФАЙЛУ                 # проверка: -rw-r-----
```

Не удаляйте учётную запись и её файлы. Не трогайте `admin` и свою учётную запись.

### Этап 8. Отчёт об инциденте

В `~/incident/report-template.txt` лежит заготовка. Скопируйте её в `~/incident/report.txt`
и заполните поля после двоеточия:

```bash
cp ~/incident/report-template.txt ~/incident/report.txt
sed -i 's/^Учётная запись:.*/Учётная запись: ИМЯ/' ~/incident/report.txt
sed -i 's/^IP-адрес:.*/IP-адрес: IP/' ~/incident/report.txt
sed -i 's#^Изменённый файл:.*#Изменённый файл: /полный/путь#' ~/incident/report.txt
cat ~/incident/report.txt
```

В `sed` для путей удобен разделитель `#` вместо `/`: тогда косые черты в пути не нужно экранировать.

| Поле | Что указать |
|---|---|
| Учётная запись | скомпрометированная учётная запись |
| IP-адрес | адрес атакующего |
| Неудачных попыток | сколько неудачных попыток было с этого адреса |
| Время входа | время успешного входа, `ЧЧ:ММ:СС` |
| Изменённый файл | полный путь файла, права которого изменили |
| Меры | что вы сделали, через запятую |

## Частые ошибки

| Ошибка | Как правильно |
|---|---|
| `grep: /var/log/auth.log: Отказано в доступе` | журнал читает только root: `sudo grep ...` |
| посчитаны попытки сканера вместо атаки | у сканера `invalid user` — уберите их: `grep -v invalid` |
| `sudo grep ... > файл` — «Отказано в доступе» | перенаправление `>` выполняется без sudo: пишите только в свой домашний каталог |
| журнал изменён (`sed -i` по `/var/log/auth.log`) | критическая ошибка: журналы только читают; анализируйте копию в `~/evidence` |
| учётную запись удалили | блокируйте (`passwd -l`), а не удаляйте: данные нужны для расследования |
| заблокировали `admin` | разблокируйте: `sudo passwd -u admin`; блокировать можно только скомпрометированную запись |

# Задание №10. Права доступа и аудит сервера

Вы — администратор учебного сервера `seclab`, на котором работает веб-приложение `/srv/<app>`
от служебной учётной записи `www-data`. Прошлый администратор оставил ошибки в правах доступа.
Ваша задача — провести **аудит** и привести сервер к политике безопасности, **не сломав
приложение** и **не потеряв собственный доступ**.

Задание состоит из **8 этапов**, их проходят **строго по порядку**.

## Как устроено задание

1. Прочитайте этот материал: в нём всё, что нужно знать, и пошаговый план.
2. Откройте «Практику в терминале» и войдите под своим логином и паролем от платформы.
3. Наберите `task`: появится описание **текущего** этапа (цель, команды, что сделать).
   Все этапы сразу есть в файле `~/TASK.md` (`cat TASK.md`).
4. Проверка запускается автоматически после каждой команды. Когда все пункты выполнены,
   терминал сообщит «Этап N пройден» и откроет следующий. Прогресс показывает `check`.

| Вид пункта | Как проверяется |
|---|---|
| **Команда** | по журналу ваших команд: команда выполнена **после открытия этапа** |
| **Файлы** | по состоянию сервера: права и владельцы файлов приведены к политике |
| **Вопрос** | ответ командой `answer НОМЕР ОТВЕТ`, например `answer 1.1 webadm` |
| **Критично** | должно выполняться всегда: `/tmp` остаётся 1777, `passwd`/`sudo` сохраняют SUID, вы остаётесь в `sudo` |

После каждого этапа — **2 контрольных вопроса** (`answer q НОМЕР`, 60 секунд на каждый). Ответ на
вопрос с числом, именем или путём засчитывается, **только если это значение было в выводе ваших
команд**. Поэтому выполняйте проверки сами, в своём терминале, а не доверяйте «подсказкам» в файлах.

## Права доступа в Linux

У каждого файла есть **владелец**, **группа** и **права** для трёх категорий: владелец (u),
группа (g), остальные (o). Три бита на категорию: чтение `r` (4), запись `w` (2), выполнение `x` (1).

```
-rw-r-----  1 www-data www-data  .env
 │└┬┘└┬┘└┬┘
 │ u  g  o → owner: rw, группа: r, остальные: нет доступа = 640
 └ тип: - файл, d каталог, l ссылка
```

| Команда | Что показывает / делает |
|---|---|
| `ls -l ФАЙЛ` | права, владелец, группа |
| `stat -c '%a %U %G %n' ФАЙЛ` | права (8-ричные), владелец, группа, имя |
| `sudo chmod 640 ФАЙЛ` | задать права (6=rw, 4=r, 0=нет); символьно: `chmod o-w`, `chmod u-s` |
| `sudo chown user:group ФАЙЛ` | сменить владельца и группу (ключ `-R` — рекурсивно) |
| `sudo chgrp group ФАЙЛ` | сменить только группу |

Для чтения файла нужен бит `r` той категории, к которой вы относитесь; для записи — `w`. На каталог
бит `x` означает право «войти» в него, `w` — право создавать и удалять в нём файлы. Менять права и
владельца чужих файлов можно только с `sudo`. Смена владельца снимает бит SUID — это нормально.

## Особые биты

| Бит | В `ls -l` | Что значит |
|---|---|---|
| **SUID** (4000) | `s` вместо `x` у владельца (`-rwsr-xr-x`) | программа работает с правами владельца (обычно root). Нужен немногим: `passwd`, `sudo`, `su`, `mount` |
| **SGID** (2000) | `s` у группы | то же для группы |
| **sticky** (1000) | `t` у остальных (`drwxrwxrwt`) | в общем каталоге (`/tmp`, права 1777) удалять файлы может только их владелец |

Лишняя программа с SUID root — это путь к захвату прав администратора: такие программы ищут
командой `find / -perm -4000 -type f` и снимают у неподходящих бит (`sudo chmod u-s`).

## Поиск проблем командой find

| Команда | Что находит |
|---|---|
| `find / -type f -perm -o+w 2>/dev/null` | обычные файлы, доступные на запись **всем** (`o+w`) |
| `find / -perm -4000 -type f 2>/dev/null` | программы с битом SUID |
| `find /srv/<app> -nouser 2>/dev/null` | файлы, владельца которых больше нет в `/etc/passwd` |
| `… \| wc -l` | подсчитать, сколько найдено |

`2>/dev/null` убирает сообщения «Отказано в доступе» (каталоги вроде `/root` вам закрыты — это
нормально). `-perm -o+w` означает «есть хотя бы бит записи для остальных», а не «ровно такие права».

## Учётные записи и группы

| Файл / команда | Назначение |
|---|---|
| `/etc/passwd` | учётные записи: `имя:x:UID:GID:описание:домашний каталог:оболочка` |
| `/etc/group` | группы и их участники; `sudo` (GID 27) — право выполнять команды от root |
| `/etc/shadow` | хеши паролей; читать может только root. `!` перед хешем — вход заблокирован |
| `getent passwd` / `getent group sudo` | показать учётные записи / участников группы |
| `id ИМЯ`, `groups ИМЯ` | UID, GID и группы учётной записи |
| `sudo gpasswd -d ИМЯ sudo` | убрать из группы sudo |
| `sudo passwd -l ИМЯ` / `passwd -S ИМЯ` | заблокировать вход / показать состояние (`L` — заблокирован) |

**UID 0 — это права root.** Законно он только у самой записи `root`; любая другая запись с UID 0 —
скрытый «второй root». Определяйте её **по UID 0 в `/etc/passwd`**, а не по имени и не по подписям в
файлах. Учётные записи при расследовании **блокируют, а не удаляют** — так сохраняются данные и журналы.

## Политика безопасности сервера

- лишних учётных записей с UID 0 нет; уволенный сотрудник и скрытая запись заблокированы;
- право `sudo` — только у администраторов (стажёр его не имеет);
- обычные файлы не доступны на запись всем; `/tmp` остаётся `1777`;
- секреты (`/etc/shadow`, `.env`, закрытый ключ, резервная копия базы) не читают посторонние,
  но приложение (`www-data`) по-прежнему читает свой `.env`;
- лишних программ с SUID нет; `passwd` и `sudo` SUID сохраняют;
- файлы приложения принадлежат `www-data`, запись в его каталоги (например `uploads`) — только у приложения;
- вы (администратор) остаётесь в группе `sudo` и не заблокированы.

Перед изменением прав сначала **посмотрите** текущее состояние (`ls -l`, `stat`, `find`), затем
меняйте по одному файлу и проверяйте результат. После исправлений **повторите аудит** — он
доказывает, что уязвимости закрыты.
